# Контракт ZiFi ESP32-S3 native

Двоичный контракт UART сохранён совместимым с существующими Z80-программами.
Источник общих констант и процедур Z80 находится в `shared/z80`.

Кадр в обе стороны:

```text
5A CMD LEN_L LEN_H DATA... CSUM
```

`CSUM` — XOR команды, двух байтов длины и payload; синхробайт `5A` в сумму не
входит. Максимальный payload — 1024 байта. UART0 работает на 115200 8N1 через
`RX=GPIO44`, `TX=GPIO43`.

## Команды Z80 -> ESP

| CMD | Команда | Ответ |
|---:|---|---|
| `00` | `ECHO` | кадр `00` с тем же payload |
| `01` | `WIFI_CONNECT`, `ssid\0password\0` | `FE`, затем `81` |
| `02` | `SYS_INFO` | `FE`, затем `82` |
| `03` | `WIFI_INI`, полный `zifi.ini` | `FE`, затем `83` |
| `04` | `PING` | `F0` |
| `05` | `GET_STEP` | `85` |
| `06` | `FTP_START`, `[port LE16][user\0][password\0]` | `FE`, затем `86` |
| `07` | `FTP_STOP` | `FE`, затем `87` |
| `08` | `UPDATE_START` | `FE`, затем `88` |
| `09` | `UPDATE_STOP` | `FE`, затем `89` |
| `0A` | `FTP_RAM_STATS` | `FE`, затем `8A` |
| `0B` | `SMB_START`, `[port LE16][share\0][host\0][workgroup\0][user\0][password\0]` | `FE`, затем `8B` |
| `0C` | `SMB_STOP` | `FE`, затем `8C` |
| `0D` | `ONLINE_UPDATE`, автономная установка из GitHub | `FE`, события `65`, затем `8D` |
| `0F` | `SYS_RESET` | `FE`, flush UART, reset |
| `10` | `NET_OPEN`, `host\0[port LE16]` | `FE`, затем `90` |
| `11` | `NET_SEND`, произвольные байты | `FE`, затем `91` |
| `12` | `NET_RECV`, `[wanted LE16]` | `92` без промежуточного ACK |
| `13` | `NET_CLOSE` | `FE`, затем `93` |
| `14` | `NET_HTTP_GET`, `host\0 + port LE16 + path\0` | `FE`, затем `94` |
| `20` | `NET_PING`, `host\0` | `FE`, затем `A1` |
| `21` | `NET_IP_CONFIG` | `FE`, затем `A0` |
| `22` | `NET_NTP` | `FE`, затем `A2` |
| `23` | `NET_PROXY_STATUS` | `FE`, затем `A3` |
| `24` | `WEATHER_GET` | `FE`, затем `A4` |
| `25` | `WCU_START`, `repo\0branch\0dir\0[protected\0...]\0` | `FE`, затем `A5`; события `67`/`68` |
| `26` | `WCU_APPLY`, номера строк списка по байту | `FE`, затем `A6`; события `67`/`68` |
| `27` | `WCU_STOP` | `FE`, затем `A7` |
| `28` | `WCU_SYNC` | `FE`, затем `A8`; события `67`/`68` заново |

`WIFI_INI` разбирает `ssid:`, `password:`, `time:`, `proxy_ip:` (или `proxy_host:`) и `proxy_port:` (по умолчанию `49281`), сохраняя полный исходный
файл в LittleFS. Повторный файл с той же длиной и CRC flash не переписывает.
При следующем reset прошивка сама восстанавливает Wi-Fi. Результат подключения
`81/83` имеет пять байтов: `[status][IPv4 x4]`; `status=0` означает ошибку.

`NET_PROXY_STATUS` возвращает статус прокси и строку адреса:
`[status(1B)][endpoint(ASCII)]`.
Статус равен: `0` — прокси отключён (в ini нет параметров `proxy_ip`),
`1` — прокси включён и проверен (сервер ответил на TCP probe),
`2` — прокси отключён из-за недоступности сервера (probe timeout / failure).

`NET_NTP` возвращает ровно 14 ASCII-цифр `YYYYMMDDhhmmss`. Часовой пояс уже
применён по целому значению `time:` в диапазоне `-14..+14`. При ошибке ответ
содержит 14 нулей; перед ним прошивка может послать `EE` с кратким текстом.

`NET_HTTP_GET` возвращает семь байтов:
`[status][HTTP code LE16][Content-Length LE32]`. Заголовок HTTP разбирает ESP,
а тело остаётся в TCP и забирается командами `NET_RECV` порциями до 1023 байт.
Первый байт `NET_RECV` равен единице только после настоящего EOF; нулевая длина
при живом сокете означает временное отсутствие данных.

`WEATHER_GET` возвращает запись погоды для заставок Wild Commander
(`Weather screensaver/build/WEATHER.WMF`, `Weather screensaver VDAC2/build/WEATHER2.WMF`).
Место задаётся в `zifi.ini` ключом `city:` — название города или посёлка
по-английски, в современном написании (`Kyiv`, `Odesa`, `Moscow`, `Rome`);
необязательный `country:` (код страны ISO, например `UA`) сужает поиск
страной. С версии 0.6.93 ESP ищет название геокодером Open-Meteo:

```text
http://geocoding-api.open-meteo.com/v1/search?name=<название>&count=1&language=en&format=json[&countryCode=<страна>]
```

Берётся первое место ответа — из одноимённых обычно самое крупное (`Paris`
без страны — Франция, с `country: US` — Техас); на экране его название на
языке запроса («Kyiv»; у маленьких мест без перевода — местное название).
Геокодер сравнивает название с именами на языке запроса, поэтому название
кириллицей («Одесса») ESP ищет с `language=ru` — и на экране оно тоже
по-русски. Значение `city:` может быть в UTF-8, CP866 (редактор Wild
Commander) или CP1251 (Блокнот «ANSI»): ESP сама переводит его в UTF-8.

Без `city:` работает способ 0.6.92: `country:` и `zip:` (почтовый индекс)
ищутся в справочнике `api.zippopotam.us/<страна>/<индекс>` (берётся последнее
место списка — для итальянских CAP это коммуна). ESP помнит координаты, пока
`city:`/`country:`/`zip:` не изменятся; место, которого справочник не знает,
тоже запоминается и повторно не запрашивается.

Прогноз `api.open-meteo.com/v1/forecast` по готовым координатам берётся заново
на каждую команду: заставка просит его при запуске и затем раз в час. Все три
запроса идут по HTTP/80 и через прокси из ini, если он задан. Ответ `A4` — 90
байт (little-endian):

```text
+0  status: 1 — данные есть, 0 — ошибка (тогда ответ короткий: [0][версия])
+1  версия формата = 1
+2  название места, CP866, ноль в конце, 24 байта (Є є Ї ї Ў ў — #F2..#F7,
    І і — латинские I i, Ґ ґ — Г г)
+26 температура, °C, знаковый байт
+27 код погоды WMO
+28 1 — день, 0 — ночь
+29 ветер, км/ч x10, u16
+31 осадки за час, мм x10, u16
+33 давление у поверхности, мм рт. ст., u16
+35 восход: час, минута
+37 закат: час, минута
+39 местное время данных: час, минута
+41 число дневных записей (6: сегодня и пять следующих дней)
+42 дневные записи по 8 байт: число, месяц, день недели (0 — понедельник),
    код WMO, минимум °C, максимум °C, осадки за сутки мм x10 u16
```

Причина ошибки уходит докладом `EE` перед ответом: `weather:no city in ini`,
`weather:no wifi`, `weather:city: not found` (такого названия геокодер не
знает), `weather:zip: not found` (индекса нет), `weather:city: http 503`,
`weather:meteo: reply timeout` и т. п.
Неудачный HTTP-запрос (ответ 5xx или 429, обрыв связи) ESP
повторяет до трёх раз с паузами 1 и 2 секунды; новые попытки начинаются только
в первые 30 секунд команды, поэтому ответ приходит раньше, чем заставка
перестаёт его ждать (90 секунд). Ответ 4xx не повторяется.

`FTP_START` с пустым payload использует порт `21` и пару `zx`/`zx`. Совместимый
`ZIFIFTP.WMF` передаёт эти значения явно. Управляющий listener создаётся только
после этой команды. Для data-канала поддерживаются active `PORT/EPRT` и passive
`PASV/EPSV`. Сервер принимает до трёх управляющих сессий; каждому занятому
слоту соответствует свой passive-порт из диапазона `2122–2124`. Файловые
команды всех сессий выполняются последовательно через единственный VFS-тракт.

`SMB_START` с пустым payload использует порт `445`, ресурс `SD`, имя `ZX-Evo`,
группу `WORKGROUP` и пару `zx`/`zx`. Ответ `8B` имеет формат
`[status][port LE16][nbns]`: последний байт равен единице, если ESP удалось
занять UDP/137 и отвечать на NBNS-запросы имени. Файловый SMB работает по
TCP/445 и при `nbns=0`, но подключаться тогда нужно по IP.

`UPDATE_START` закрывает FTP, SMB и обычный TCP-клиент, при необходимости ждёт
сохранённое Wi-Fi-подключение и открывает одноразовый listener `8267`. Ответ
`88` содержит семь байтов:

```text
[status][IPv4 x4][port LE16]
```

`UPDATE_STOP` закрывает listener и возвращает `89 [01]`. OTA и FTP одновременно
не работают; сетевой updater не владеет UART.

`ONLINE_UPDATE_CHECK` (`0E`) не пишет Flash. ESP загружает опубликованный
`firmware/firmware.sha256`, содержащий `VERSION <build>` и строки SHA. Ответ
`8E` имеет вид `[status][relation][version ASCII]`, где `relation`: 0 — версии
одинаковы, 1 — опубликованная новее, 2 — опубликованная старее, 3 — разные
несравнимые сборки.

`ONLINE_UPDATE` (`0D`) не принимает URL из Z80. После подтверждения ESP повторно
загружает манифест, находит строку именно для `firmware.bin`, а затем получает
образ из `raw.githubusercontent.com` ветки `main`. Событие `65` содержит
`[stage][percent]`: этапы 1 — manifest, 2 — образ, 3 — итоговая проверка и
установка. Ответ `8D` имеет вид
`[status][SHA-256 32 bytes]`. При успехе ESP физически отправляет этот ответ по
UART и только затем перезапускается.

Совпадение версии не отменяет операцию: пользователь может заново установить
тот же опубликованный образ. В неактивный OTA-раздел пишется только
application-образ с корректным заголовком ESP32-S3. Несовпадение SHA-256,
обрыв, неверная длина или ошибка Flash вызывают `Update.abort()`; загрузочный
слот не переключается.

`SYS_INFO` сообщает внутреннюю RAM, PSRAM, Flash, размер приложения, причину
reset, назначение ядер, фактическое размещение межъядерного буфера и один build
identifier после маркера `FW:`.

### Проверка и обновление Wild Commander (`WCU_*`)

Плагин `WC Update/build/WCUPDATE.WMF` — аналог `sfc /scannow` для Wild
Commander Improved. Всю работу ведёт ESP; Z80 только отвечает на файловые
запросы, показывает список и отдаёт номера отмеченных файлов.

`WCU_START` (`25`): `repo\0branch\0dir\0`, затем защищённые пути (каждый с
нулём) и пустая строка. Плагин шлёт
`andrewinsidelazarev/Wild-Commander-Improved`, `main`, `exe`, `WC/wc.ini`.
ESP останавливает FTP, SMB и прежний сеанс, требует подключённый Wi-Fi и
запускает задачу; ответ `A5 [1]` означает, что задача идёт. Дальше без команд:

1. `GET /repos/{repo}/git/ref/heads/{branch}` — коммит ветки;
   `GET /repos/{repo}/git/trees/{commit}:{dir}?recursive=1` — список
   (api.github.com, HTTPS, до 96 файлов, JSON до 64 КиБ; неполный или
   испорченный ответ — отказ целиком, как и пути, различающиеся только
   регистром: на FAT это один файл). Ответ 403/429 — `GitHub API limit`.
2. Опись SD по каталогам из списка (`OPENDIR`/`READDIR`). Файлы, которых нет
   на GitHub, показываются только внутри каталогов WC (не в корне карты);
   не влезшие в таблицу отмечаются в итоге (`SD list cut`). Отказ `OPENDIR`
   перепроверяется `STAT`: каталог есть — опись недостоверна, проверка
   кончается ошибкой, а не объявляет его файлы новыми.
3. Для файла одинаковой длины — git-SHA-1 (`SHA1("blob <size>\0" + данные)`)
   по чтению с SD окнами `OPEN`/`READ_WINDOW`; перед чтением длина файла по
   записи каталога (`STAT`) сверяется с GitHub. Другая длина — «отличается»
   без чтения. Каждая строка уходит событием сразу после сверки.

`WCU_APPLY` (`26`): номера строк по байту. Для каждого файла, который можно
обновить: скачать с `raw.githubusercontent.com/{repo}/{commit}/{dir}/{path}`
(до трёх раз, пока SHA не совпадёт) → создать недостающие каталоги (`STAT`,
`MKDIR`) → записать во временный `WCUPD.TMP` того же каталога и прочитать
обратно (до трёх раз, пока SHA не совпадёт) → заменить файл копией →
прочитать файл и сверить SHA ещё раз; при несовпадении весь круг повторяется
один раз.

Замена — `VFS_MOVE_RENAME` (`5D`) с REPLACE: FILEX Wild Commander Improved
перенаправляет запись файла на цепочку копии одной записью сектора, а при
сбое записи возвращает прежнюю, так что имя файла не пропадает ни на миг.
Ответ `25` — перенос состоялся (не освободилась лишь старая цепочка);
`10..1D` и отказ плагина `01` — ничего не менялось, копия удаляется, файл
`FAILED`. Сбой носителя (`20..24`, `26`) или обрыв связи — исход неизвестен:
итог проверяется чтением файла; файл верный и копии нет — перенос лёг.
Иначе копия не удаляется (при неподтверждённом откате `24` на её цепочку может
остаться вторая ссылка), остальные файлы не пишутся, и приходит событие
ошибки `check the disk`.

Плагин без FILEX MOVE отвечает на `5D` статусом `FE`, ничего не трогая; тогда
ESP идёт запасным путём на `VFS_RENAME`: прежний файл откладывается под
именем `WCUPD.OLD` (имя должно быть свободно), копия получает имя файла, и
лишь потом `WCUPD.OLD` удаляется. `VFS_RENAME` отвечает кодом WC, но любой
отказ здесь — исход неизвестен: даже у WC Improved код отказа (`A=0`) бывает
и после того, как удаление прежней записи легло, а откат убрал новую. Поэтому
после отказа ни одна копия не удаляется (если прежний файл уже отложен,
делается попытка вернуть его на имя), запись в сеансе прекращается, и
приходит ошибка `rename failed: CHKDSK`. Не удалился `WCUPD.OLD` — файл
обновлён, но каталог с остатком только для чтения уже в этом сеансе.
Защищённый файл (`wc.ini`) ставится только тогда, когда STAT подтвердил, что
его на SD нет; нашёлся при записи — только сверяется (`5`/`6`), не заменяясь.

Остатки прерванной замены (`WCUPD.TMP`, `WCUPD.OLD`) в список не попадают и
не удаляются: после сбоя с неподтверждённым откатом такой остаток может делить
цепочку кластеров с файлом, и его удаление освободило бы данные файла. Опись
ищет их в листинге и ещё прямым `STAT` в каждом каталоге (ошибка чтения
посреди каталога для WC выглядит его концом); найдя, запрещает запись в
каталог (`CHKDSK: old WCUPD.* in folder`), а итог проверки напоминает
`CHKDSK: old WCUPD.*`. Перед записью копии имя `WCUPD.TMP` проверяется `STAT`,
предварительного удаления нет, а `OPEN` на запись в плагине WC Update
занятое имя не берёт (см. `VFS_OPEN` ниже): остаток, не замеченный описью из-за
ошибок чтения, не освобождается и записью поверх. ESP удаляет только свою
копию — созданную `OPEN` того же шага. Каталог, который опись сочла
отсутствующим, а запись нашла, — признак ошибок чтения: запись в сеансе
прекращается (`SD read errors: CHKDSK`). Имена `WCUPD.TMP`/`WCUPD.OLD` в
эталоне GitHub — отказ списка. В итоге с неудачами — причина последнего
файла, который сейчас `FAILED` (она запоминается до уборки, и отказ удаления
копии её не подменяет), а предупреждение о карте — перед ней:
`N to update, M failed[, CHKDSK]: <причина>`.

`WCU_APPLY` принимается (`A6 [1]`), только пока задача ждёт команды и
прежний APPLY закончен; повтор той же команды плагином второй раз её не
запускает. После неизвестного исхода замены (`check the disk`) запись в этом
сеансе запрещена. Защищённый файл обновляем, пока его нет на SD, в том числе
после неудачной попытки; итог с неудачами — `N to update, M failed`, а не
«всё совпадает».

`WCU_STOP` (`27`): задача прерывается после текущего шага (незаконченная
`WCUPD.TMP` удаляется, старый файл не тронут), приём HTTPS прерывается сразу;
`A7 [1]` — задача завершилась за 20 с, `A7 [0]` — ещё работает, и плагин
просит снова (до трёх раз), всё время обслуживая файловые запросы. Остановка
не снимается следующим APPLY. Пока задача жива, `FTP_START` и `SMB_START`
отвечают отказом (`wc update stopping`): VFS-мост у них общий.

`WCU_SYNC` (`28`): события не подтверждаются, поэтому потерянное событие
плагин лечит запросом полного повтора (если идёт работа — ESP выдаёт его
после неё): метка — событие `67` с этапом `6` и полем «всего», равным числу
строк (этап, текст и полосу плагина она не меняет), затем все строки по
порядку номеров и последнее состояние. Повтор полон, только если после метки
строки пришли подряд с нуля до «всего − 1» и затем итог `4`/`FF`; иначе
просьба повторяется. Плагин просит повтор после итога каждого APPLY — и `4`,
и `FF` (строки меняются на месте, и потерю обновлённой строки по дыре не
увидеть; события этапа `5` взводят этот повтор, даже если ответ `A6`
потерялся); когда итог `4` проверки пришёл, а строк меньше, чем в поле
«всего», или в таблице дыра; когда 60 с нет ни одного пакета, пока идёт
работа (этап не `4`/`FF` или APPLY отправлен без итога). `SYNC` уходит без
ожидания ответа `A8`: ожидание снимает полный повтор, а нет его 10 с после
последнего пакета — просьба повторяется. Из-за потерь — не чаще пяти раз за
сеанс (лимит исчерпан — ошибка `list not refreshed`), после APPLY — всегда.
Пока повтор ожидается, `Enter` не принимается.

Событие `67` — состояние:

```text
[phase][current LE16][total LE16][percent][ASCII/UTF-8 text]
phase: 1 GitHub, 2 опись SD, 3 сверка SHA, 4 готово, 5 обновление,
       6 метка повтора WCU_SYNC, FF ошибка
```

Процент — доля байтов этапа: при сверке — байты, которые нужно прочитать с SD,
при обновлении — трижды размер каждого файла (запись и два чтения). Отдельное
событие ради одной полосы — не чаще раза в 250 мс. После ошибки (`FF`, текст —
причина) и после итога (`4`) задача ждёт `WCU_APPLY` или `WCU_STOP`.

Событие `68` — строка списка:

```text
[index][status][flags][size on SD LE24][size on GitHub LE24][path]
status: 1 совпадает, 2 отличается, 3 нет на SD, 4 только на SD,
        5/6 защищён (совпадает/свой), 7 ошибка чтения, 8 обновлён, 9 не удалось
flags:  1 есть на GitHub, 2 есть на SD, 4 защищён, 8 можно обновить,
        16 исполняемый (.WMF/.$C/.SPG) — отмечается клавишей A
```

Размер `FFFFFF` — 16 МиБ и больше (плагин показывает `>16M`). Путь — в UTF-8
без нуля; если он длиннее 54 байтов, приходит хвост, срезанный по границе
символа. Строки списка теряться не должны, поэтому очередь событий ESP ждёт
свободного места до 5 с. Номера строк идут в порядке списка: сам WC
(загрузчик `*.$C` в корне), плагины `*.WMF` по алфавиту (и те, что есть
только на SD), затем всё остальное по алфавиту пути; регистр не различается.

ESP теряет команду, пришедшую, пока её файловый клиент ждёт ответа Z80
(обрабатываются только `PING` и `SYS_RESET`). `ACK` уходит сразу по приёму,
поэтому плагин, не получив его за 0,5 с, отправляет команду снова (до шести
раз) и всё это время обслуживает файловые запросы. Ответ после `ACK` на
`WCU_START` и `WCU_STOP` плагин ждёт до 40 с (ESP даёт прежней задаче до
20 с закончить шаг), на `WCU_APPLY` — 5 с: ESP лишь ставит его в очередь.
`Esc` прерывает ожидание `WCU_START` и `WCU_APPLY`.

## Разделение ядер

- core 1 принимает и передаёт все UART-кадры и выполняет VFS; другого владельца
  UART нет;
- core 0 выполняет Wi-Fi events, подключение Wi-Fi, DNS, TCP/HTTP, FTP/OTA и
  UDP/NTP;
- FreeRTOS-очереди содержат только однобайтовые сигналы;
- request/response payload хранится в PSRAM, с безопасным fallback во
  внутреннюю RAM, если PSRAM не инициализировалась.

ACK для долгой сетевой команды выдаётся core 1 до постановки работы в очередь.
Готовый ответ возвращается на core 1, и только он формирует UART-кадр.
События FTP `60/61`, SMB `62/63/64`, прогресс обновления `65` и отдельная
ASCII-шкала RSSI `66` для работающего FTP или SMB также проходят через
межъядерную очередь: сетевой код core 0 не владеет UART даже для индикатора.
Событие `66` не вызывает `SYS_INFO` и не смешивает его диагностический текст с
уровнем сигнала.

## VFS: команды ESP -> Z80

VFS-клиент реализован на core 1 и сохраняет контракт существующего плагина
Wild Commander:

| CMD | Операция | Основной формат |
|---:|---|---|
| `40` | `VFS_STAT` | путь с NUL -> `[status][is_dir][size LE32][FILEX metadata:16]` |
| `41` | `VFS_OPENDIR` | путь с NUL -> `[status][dir caps]` |
| `42` | `VFS_READDIR` | пусто -> `[status][is_dir][size LE32][name][00][date LE16][time LE16]`; `[count]` -> до `count` таких кадров и итог `[02]` или `[01]` |
| `43` | `VFS_FSINFO` | `[refresh]` -> `[status][FILEX_FS_INFO:48]` |
| `44` | `VFS_FAT_WINDOW` | `[seq][raw offset LE32][raw length LE16]` -> оконный поток карты занятости активной FAT |
| `50` | `VFS_OPEN` | `[mode][path NUL]` -> `[status][legacy caps][FILEX caps]`, mode `0` read / `1` replace / `2` append / `3` FILEX |
| `51` | `VFS_READ` | `[wanted LE16]` -> `[status][data...]` |
| `53` | `VFS_CLOSE` | пусто commit, `[00]` abort |
| `54` | `VFS_DELETE` | путь с NUL -> `[status]` |
| `55` | `VFS_MKDIR` | путь с NUL -> `[status]` |
| `56` | `VFS_BLOCK` | совместимая запись RAW-блоками до 512 байт |
| `57` | `VFS_WRITE_WINDOW` | поток одного RAW-окна до 16 КиБ -> один ответ |
| `58` | `VFS_READ_WINDOW` | `[seq][wanted LE16]` -> поток одного окна до 16 КиБ |
| `59` | `VFS_RENAME` | `[attr][old path NUL][new basename NUL]` -> `[status]` |
| `5A` | `VFS_EXTEND` | `[length LE32]` -> `[status]`, legacy append нулей |
| `5B` | `VFS_SEEK` | `[absolute offset LE32]` -> `[status]` |
| `5C` | `VFS_SET_EOF` | `[size LE32]` -> `[status][actual size LE32]` |
| `5D` | `VFS_MOVE_RENAME` | `[flags][attr][old path NUL][new path NUL]` -> `[FILEX status]` |
| `5E` | `VFS_SET_METADATA` | `[FILEX metadata:16]` -> `[status][applied attr]` |

Даты записей (плагины `ZIFIFTP.WMF` v0.15 и `ZIFISMB.WMF` v0.5.10, прошивка
0.6.94). Времена FAT — местные: так их пишут и Wild Commander (по часам CMOS),
и Windows. ESP переводит их в UTC и обратно по поясу `time:` из `zifi.ini`.

- `VFS_STAT` после шести прежних байтов добавляет 16-байтовую структуру FILEX
  `GET_METADATA` Wild Commander Improved (та же раскладка, что у
  `VFS_SET_METADATA`: атрибут, create tenth/time/date, access date, write
  time/date). Без этой операции FILEX (старый WC) плагин отвечает прежними
  шестью байтами, и ESP считает даты неизвестными. У корня записи нет, даты тоже.
- `VFS_READDIR` за именем пишет ноль, затем дату и время записи — поля API 58,
  запрошенные с битом 6 маски: время **изменения** (+22/+24), которое
  показывает панель WC. Старое ядро бит 6 не знает и отдаёт время создания в той
  же раскладке. Старая прошивка берёт имя до конца пакета и на этом нуле
  заканчивает C-строку; новая признаёт хвост при длине ответа от 12 байт и нуле
  на месте `length - 5` — в ответе старого плагина там стоит буква имени.
- `VFS_OPEN` режима `3` FTP-плагин поддерживает только ради `SET_METADATA`
  (команда `MFMT`). Прежний FTP-плагин любой ненулевой режим понимал как запись
  и удалил бы файл, поэтому ESP шлёт режим `3` FTP-плагину, только если `VFS_STAT`
  уже вернул метаданные: так отвечает лишь новый плагин. Режим `2` и неизвестные
  режимы новый FTP-плагин отклоняет, не трогая диск.

Пакетный `VFS_READDIR` (плагин `ZIFISMB.WMF` v0.5.10, прошивка 0.6.94). Второй
байт ответа `VFS_OPENDIR` — возможности обхода, бит 0 — READDIR умеет пачку.
Старый плагин отвечает одним статусом, старая прошивка читает только его.
Тогда `VFS_READDIR` несёт один байт — сколько записей прислать. Плагин отвечает
кадрами `VFS_READDIR` прежнего вида подряд, а за ними — кадром-итогом из
одного байта: `02` — пачка полна, каталог продолжается; `01` — каталог
кончился (записей в такой пачке может быть меньше или ни одной). Пустой
`VFS_READDIR` по-прежнему означает одну запись. Z80 ищет следующую запись,
пока предыдущая идёт по линии, ESP держит пачку в памяти и отдаёт записи мосту
по одной, а обмен «запрос — ответ» остаётся один на пачку.

Успешный `VFS_OPEN` может вернуть один, два или три байта. Второй байт —
legacy-возможности: бит 0 разрешает `VFS_WRITE_WINDOW`, бит 1 —
`VFS_READ_WINDOW`, бит 2 — `VFS_EXTEND`. Если второго байта нет, прошивка
автоматически использует старые `VFS_BLOCK` и `VFS_READ`.

Третий байт — маска API 77 FILEX: биты 0..5 означают соответственно
`READ_AT`, `WRITE_AT`, `SET_EOF32`, `GET_FS_INFO`, `MOVE_RENAME` и
`SET_METADATA`; бит 6 разрешает current-directory replace, бит 7 —
`READ_FAT`. Режим `VFS_OPEN=3` требует установленного `FILEX.WMF`; при
отсутствии провайдера открытие завершается статусом `NO_CONTEXT=#15`.

Каждый запрос `VFS_WRITE_WINDOW` содержит один фрагмент окна:

```text
[flags][seq][offset LE16][total LE16][crc16 LE16][data <= 1016]
```

В `flags` бит 0 означает первый кадр, бит 1 — последний. `total` находится в
диапазоне 1..16384 для legacy-режимов 1/2 и 1..16352 для FILEX-режима 3:
первые 32 байта 16-КиБ страницы заняты параметрами API 77. Смещения кадров
идут подряд, а CRC-16/CCITT-FALSE всего окна записывается в последний кадр.
Промежуточных ответов нет. После проверки окна Z80 отвечает ровно один раз:

```text
[status][seq][accepted LE16]
```

В legacy-режимах 1/2 полное окно 16 КиБ подтверждается только после
завершения API 76 `APPEND`; короткий хвост публикуется при
`VFS_CLOSE(commit)`. В режиме 3 каждое окно подтверждается после завершения
FILEX `WRITE_AT` по текущему абсолютному смещению.

Режим `VFS_OPEN=2` не удаляет существующую FAT-запись и продолжает запись теми
же `VFS_WRITE_WINDOW` с физического конца файла. `VFS_RENAME` принимает только
новое имя без пути: API Wild Commander умеет переименование внутри текущего
каталога, но не перенос между каталогами.

Плагин обновлятора `WCUPDATE.WMF` режим `1` понимает как «создать новый»:
прежний файл не удаляется, занятое имя — отказ `01` (MKFILE Wild Commander;
WC Improved отказывает и при ошибке чтения каталога). Обновлятор пишет только
свою копию `WCUPD.TMP`, и остаток прошлой замены, который может делить цепочку
с файлом, так не освобождается записью поверх, даже если опись его не увидела.

Кадр `VFS_READDIR` пустой или со статусом `00`, но короче шести байтов, —
сбой обмена: прошивка 0.6.94 считает его ошибкой, а не концом каталога, иначе
перечень молча обрезался бы.

Режим `VFS_OPEN=3` находит существующую запись файла или каталога и создаёт
контекст FILEX. `VFS_SEEK` задаёт абсолютное смещение следующих
`VFS_READ_WINDOW`/`VFS_WRITE_WINDOW`; предыдущие байты файла при этом не
читаются. `VFS_SET_EOF` поддерживает размер 0, усечение и нулевое расширение.
`VFS_MOVE_RENAME` принимает два полных пути, переносит объект между каталогами
и по биту 0 флага разрешает атомарную замену назначения.

`VFS_FSINFO` возвращает после статуса исходную 48-байтовую структуру FILEX
версии 1: флаги носителя, sectors-per-cluster, bytes-per-sector, числа
кластеров, serial, 11-байтовую метку, число секторов и состояние FAT/FSInfo.
`refresh.bit0` зарезервирован FILEX; ESP сам запрашивает
`VFS_FAT_WINDOW`, если `Free_Count` неизвестен.

`VFS_FAT_WINDOW` читает через FILEX выбранную активную FAT окнами
до 31 сектора. `raw offset` и `raw length` кратны 512. Z80 сжимает
каждые 8 FAT32-записей в один байт: значение бита `0` означает свободную
запись, `1` — занятую. Ответ использует тот же 9-байтовый заголовок, порядок
кадров и CRC, что `VFS_READ_WINDOW`; `total` равен `raw length / 32`.

В `VFS_MOVE_RENAME` второй байт равен `00` для файла или `10` для каталога,
затем идут два NUL-терминированных полных пути. `VFS_SET_METADATA` переносит
16-байтовую FILEX-структуру: size, маску/значение FAT-атрибутов, маску времён,
create tenth/time/date, access date и write time/date. Ответ сообщает
фактически применённые атрибуты.

Для `VFS_READ_WINDOW` legacy-режим читает до 32 секторов через `LOAD512`, а
режим 3 выполняет FILEX `READ_AT` непосредственно по текущему смещению. Оба
пути возвращают одинаковую последовательность кадров:

```text
[status][flags][seq][offset LE16][total LE16][crc16 LE16][data <= 1015]
```

Флаги имеют то же значение; поле CRC содержит контрольную сумму всего окна.
ESP проверяет последовательность, длину и CRC до публикации окна сетевому
серверу.

Старый `VFS_BLOCK` оставлен для двусторонней совместимости. Его первый
фрагмент имеет формат:

```text
[00][seq][raw_len LE16][stored_len LE16][crc16 LE16][data <= 248]
```

Продолжение:

```text
[80][seq][offset LE16][data <= 252]
```

После каждого фрагмента Z80 отвечает `[status][seq][accepted LE16]`.
Используется CRC-16/CCITT-FALSE. Код `52` оставлен для старого raw-протокола и
не переиспользуется.

Сеть не вызывает VFS напрямую. Она ставит асинхронный управляющий запрос core 1
и обменивается bulk-данными через два SPSC-кольца по 64 КиБ в PSRAM:

```text
Network/core 0 -> NetworkToVfs -> VFS/UART/core 1
Network/core 0 <- VfsToNetwork <- VFS/UART/core 1
```

Операция записи читает окно непосредственно из `NetworkToVfs` по смещению и
удаляет байты из кольца только после единственного успешного ответа Z80.
Чтение публикует кадры непосредственно в `VfsToNetwork`; отдельный 16-КиБ
буфер во внутренней RAM не создаётся. `CLOSE(commit)` отклоняется, пока во
входном кольце есть необработанный хвост. Это сохраняет backpressure и не
допускает тихого усечения файла при отказе UART или медленной SD.

### Семантика сохранения и перезаписи SMB2/SMB3
- **Создание и перезапись файлов (`FILE_OVERWRITE_IF` / `FILE_SUPERSEDE`):**
  Сервер не создаёт фиктивный 0-байтовый файл на этапе `SMB2_CREATE`. При первом
  `SMB2_WRITE` со смещением 0 файл открывается в режиме последовательной записи
  (Mode 1 / `kOpenWrite`), при которой Wild Commander выделяет цепочку кластеров
  через `FN_APPEND`. При `SMB2_CLOSE` выполняется `kCloseCommit`, фиксирующий
  финальный размер и дату в каталоге FAT32.
- **Произвольная запись (`offset > 0`):**
  Используется позиционный режим Mode 3 (`kOpenRandom` / `FILEX_OP_WRITE_AT`).
- **Дескрипторы безопасности (`SMB2_0_INFO_SECURITY`):**
  Сервер возвращает `SMB2_STATUS_NOT_SUPPORTED`, что полностью совместимо со
  стандартными Windows клиентами и предотвращает ложные сбои навигации в проводнике.
- **Опрос емкости тома (`loadFsInfo` / `SMB2_FILE_FS_SIZE_INFORMATION`):**
  Сервер запрашивает базовую геометрию тома через `kGetFsInfo (flags=0)` за ~1 мс.
  Если в FSInfo секторе FAT32 счётчик свободных кластеров не инициализирован,
  сервер не запускает блокирующее 60-секундное сканирование FAT по UART, а отдаёт
  валидное значение немедленно, обеспечивая мгновенный первый отклик (< 0.1 с).
- **Обновление метаданных (`SMB2_SET_INFO`):**
  Ошибки обновления атрибутов и временных меток FAT обрабатываются как best-effort
  и не приводят к срыву закрытия (`SMB2_CLOSE`) или отказу сохранения уже записанных данных.

## TCP-протокол OTA

После запуска `update.sna` PC подключается к адресу из ответа `88`:

```text
ESP -> PC: ZIFI-OTA/1 <build> <maximum_size>\n
PC -> ESP: BEGIN <size> <sha256_hex>\n
ESP -> PC: READY 1024\n
PC -> ESP: <ровно size байтов firmware.bin>
ESP -> PC: OK <sha256_hex>\n
```

При любой ошибке ESP отвечает `ERR <reason>`. До erase проверяется, что это
application-образ с magic `E9`, chip id ESP32-S3 и `esp_app_desc_t` по смещению
32; поэтому объединённый factory-образ не принимается. Затем данные пишутся в
неактивный слот и параллельно хэшируются через SHA-256. Несовпадение, timeout,
обрыв или короткая запись вызывают `Update.abort()` и не меняют загрузочный
слот.

После полного SHA и успешного `Update.end(false)` ESP отвечает `OK` и
перезагружается. Arduino-автоподтверждение отключено: новый слот становится
валидным только после запуска UART, VFS-моста и сетевой задачи. Иначе включённый
bootloader rollback возвращает предыдущую прошивку. WebDAV пока не поднимается.
На неизвестную UART-команду приходит `EE unsupported:<CMD>`.

SHA-256 защищает целостность, но не аутентифицирует отправителя. Поэтому порт
открывается только с экрана `update.sna`, а обновление следует выполнять в
доверенной локальной сети и затем закрывать экран updater.

## Образы Flash

`firmware.factory.bin` содержит bootloader, таблицу разделов, начальное OTA
состояние и приложение; он записывается с адреса `0x0`. `firmware.bin` — только
application image: при factory-установке он находится в `app0`, а updater пишет
его в текущий неактивный слот (`app0` или `app1`). Оба слота имеют размер
`0x1E0000`; `firmware.factory.bin` через OTA передавать запрещено.
