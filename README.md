# ZiFi ESP32-S3 Zero

<p align="center">
  <img src="Zifi%20ESP32%20Zero%20Adapter/Documentation/esp32-s3-zero-to-esp-01-adapter.webp" alt="ZiFi ESP32-S3 Zero to ESP-01S Adapter" width="700">
</p>

Нативная прошивка для стандартного Waveshare ESP32-S3-Zero на
`ESP32-S3FH4R2` (4 МБ Flash, 2 МБ QSPI PSRAM). Модуль устанавливается вместо
ESP-01S через переходник и сохраняет двоичный UART-протокол ZiFi.

Текущая версия реализует двоичный протокол ZiFi, NTP, HTTP-транспорт
`zifi.spg`, FTP и SMB2/SMB3 поверх двухъядерного VFS-моста:

- UART0: `RX=GPIO44`, `TX=GPIO43`, 115200 8N1;
- команды `ECHO`, `WIFI_CONNECT`, `WIFI_INI`, `PING`, `SYS_INFO`, `GET_STEP`,
  `FTP_START/STOP`, `FTP_RAM_STATS`, `SMB_START/STOP`, `NET_OPEN/SEND/RECV/CLOSE`,
  `NET_HTTP_GET`, `NET_PING`, `NET_IP_CONFIG`, `NET_NTP`, `NET_PROXY_STATUS`,
  `UPDATE_START/STOP` и `SYS_RESET`;
- прозрачный HTTP-прокси для обхода блокировок ретро-архивов (`vtrd.in`, `zxart.ee` и др.) с проверкой доступности и фиксированной авторизацией;
- прямой HTTPS на ESP32 с проверкой сервера по встроенному Mozilla CA-bundle;
  тело ответа передаётся Z80 без перекодирования и распаковки;
- NTP-плагин Wild Commander с результатом `YYYYMMDDhhmmss`;
- совместимость с Native-версией `zifi.spg`: ESP сама выполняет DNS,
  HTTP-запрос и разбор заголовка, Z80 забирает тело командами `NET_RECV`;
- FTP с тремя управляющими сессиями на задаваемом порту (обычно `21`),
  active `PORT/EPRT` и отдельными passive `PASV/EPSV`-портами `2122–2124`;
- односессионный SMB2/SMB3 на TCP/445 с NTLMSSP; signing объявлена доступной,
  но сервер её не требует (`SecurityMode=1`), ресурсом `SD`,
  ответами NBNS по UDP/137 и WS-Discovery по UDP/3702 для сетевого окружения Windows 10/11;
- мгновенный отклик при открытии шары без блокирующего 60-секундного сканирования FAT;
- надёжное сохранение и перезапись файлов (`FILE_OVERWRITE_IF` / `FILE_SUPERSEDE`):
  прямой последовательный тракт (Mode 1 / `APPEND`) с корректным выделением кластеров в FAT32
  Wild Commander и неблокирующим обновлением метаданных времени;
- VFS-клиент Wild Commander (`STAT`, каталоги, чтение, блочная запись,
  `CLOSE`, удаление, создание каталогов, append, увеличение EOF нулями и
  переименование);
- два межъядерных кольца по 64 КиБ в PSRAM для `Network -> VFS` и
  `VFS -> Network`;
- общий пул из восьми 64-КиБ рабочих PSRAM-слотов для SMB READ/WRITE и
  скользящее READ-окно: один физически обслуживаемый async-запрос, а следующие
  маленькие дескрипторы удерживают credits клиента до своего продвижения;
- сохранение полного `zifi.ini` в LittleFS только при изменении CRC;
- A/B-обновление по Wi-Fi с проверкой application-заголовка ESP32-S3,
  SHA-256 и автоматическим rollback;
- полный factory-образ для первой записи через USB.

WebDAV ещё не включён. Сетевой файловый listener запускается только явной
командой плагина: `FTP_START` для `ZIFIFTP.WMF` либо `SMB_START` для
`ZIFISMB.WMF`. Одно наличие Wi-Fi не открывает порты `21` и `445`.

## Архитектура двух ядер

```text
core 1: UART0 + frame parser + VFS client Wild Commander
       ▲                         ▲                │
       │ control queues          │ 64 KiB PSRAM   │ 64 KiB PSRAM
       ▼                         │ Network -> VFS │ VFS -> Network
core 0: Wi-Fi events + DNS + TCP/HTTP + FTP/SMB/OTA + UDP/NTP/NBNS
```

UART принадлежит только core 1. Сетевой worker никогда не пишет в UART
напрямую, поэтому ответы разных задач не могут перемешать кадры. Arduino Wi-Fi
events также закреплены за core 0. Управляющие очереди передают однобайтовые
сигналы, bulk-данные идут через два SPSC-кольца. Кольца размещаются в PSRAM;
если её инициализация не удалась, предусмотрен диагностический fallback по
4 КиБ во внутренней RAM. FTP и SMB передают между кольцом и Z80 окнами до 16 КиБ:
данные идут UART-кадрами до 1024 байт без промежуточного ACK, а целое окно
подтверждается только после CRC и записи `APPEND`. Старые команды по 512 байт
сохранены как совместимый fallback.

Сетевой producer может продолжать принимать данные в PSRAM, пока core 1 ждёт
медленную запись SD. Для обратного направления core 1 наполняет отдельное
кольцо, а сеть освобождает его независимо. `SYS_INFO` показывает ядра,
фактический тип памяти и размер обоих колец.

SMB объявляет Windows READ по 64 КиБ и WRITE до 512 КиБ. Это верхние пределы:
реальный Windows CopyFile/FAR в аппаратном тесте 0.6.86 продолжил передавать
WRITE по 64 КиБ и менять порядок их смещений. Большой WRITE сразу получает
interim `STATUS_PENDING`; остальные
асинхронные READ/WRITE получают его, если не закончены за 30 секунд. `SUCCESS`
всё равно отправляется только после физического FILEX I/O. Перед interim сервер снижает
credit target соединения до одного, поэтому Windows продлевает тайм-аут, но не
может бесконечно пополнять очередь. `CANCEL` после interim адресуется по
`AsyncId`. Core 1 проводит запрос через физические окна Wild Commander по
16 КиБ; каталожный кэш остаётся в отдельной области PSRAM.

## Программы и плагины Z80

* **`ZiFi SPG` (`ZiFi SPG/build/zifi.spg`):**
  Полноценный браузер и загрузчик для ZX-Evolution (исходники на Z80 и сборка SPG в `ZiFi SPG/`).
  Работает через двоичные команды `NET_HTTP_GET`, `NET_RECV`, `NET_CLOSE`, `WIFI_INI` и `NET_NTP`.
  ZIP-ссылки сначала проходят через серверный `unzipremote.php`: корректный
  распакованный файл сохраняется сразу, а ложный `.zip` без сигнатуры `PK`
  автоматически повторно загружается напрямую как исходный ZIP-архив.
* **`SMB Server` (`SMB Server/build/ZIFISMB.WMF`):**
  Плагин для Wild Commander, поднимающий файловый сервер Windows SMB2/SMB3 с доступом к SD-карте по сети `\\ZX-Evo\SD`.
* **`FTP Server` (`FTP Server/build/ZIFIFTP.WMF`):**
  Плагин для Wild Commander v0.13 (команда `FTP_START`), запускающий FTP-сервер с поддержкой активного и пассивного режимов и отдельной шкалой Wi-Fi.
* **`NTP Time Sync` (`NTP Time Sync/build/NTPTIME.WMF`):**
  Плагин для Wild Commander для сетевой синхронизации часов реального времени RTC.
* **`Online Update` (`Online Update/build/ZIFIUPD.WMF`):**
  Ручной пользовательский обновлятор: читает `/zifi/zifi.ini`, подключает ESP к
  Wi-Fi, показывает установленную и опубликованную версии, затем по подтверждению
  запускает прямую HTTPS-загрузку `firmware.sha256` и `firmware.bin` из GitHub.
  PC и Python не нужны; повторная установка той же версии разрешена.
* **`Update Mode` (`Update Mode/src/update.asm`):**
  Исходник совместимого обновления с PC через `tools/esp_tool.py`. Snapshot
  `firmware/update.sna` создаётся локально сборкой и не публикуется в Git.


## Сборка прошивки

```powershell
# Выполняйте из корня репозитория.
python -m pip install -r requirements-build.txt
.\build.bat
```

`build.bat` вычисляет короткий ASCII-путь к кэшу PlatformIO. Это обход
ограничения Xtensa GCC 8.4, который не открывает Arduino framework из
Unicode-пути профиля Windows; сам проект и пакеты при этом никуда не копируются.

PlatformIO автоматически создаёт:

- `firmware/firmware.bin` — приложение по адресу `0x10000`;
- `firmware/firmware.factory.bin` — объединённый образ для записи с `0x0`;
- `firmware/firmware.sha256` — опубликованная версия и SHA-256 обоих образов;
- `firmware/update.sna` — локальный игнорируемый результат сборки: экран
  включения сетевого updater на порту `8267`.

Параметры платы закреплены в `platformio.ini`: официальный совместимый профиль
`esp32-s3-devkitm-1` переопределён под 4 МБ QIO Flash и 2 МБ QSPI PSRAM.

## Сборка SMB-плагина

```powershell
& ".\SMB Server\build.bat"
```

Результат: `SMB Server/build/ZIFISMB.WMF` v0.5.8. Прошивка
`s3-native-0.6.87` с выключенным диагностическим кольцевым журналом
подтверждает READ и WRITE только после полного сетевого запроса: Windows
CopyFile не повторяет остаток короткого успешного ответа ни для чтения, ни для
записи. При задержке свыше 30 секунд сервер посылает промежуточный
`STATUS_PENDING`, чтобы Windows не оборвала обычный файловый запрос на
60-секундной границе. Это не раннее подтверждение данных: финал приходит после
FILEX, а после interim точный `CANCEL` обрабатывается по `AsyncId`. Credit target
временно равен одному, поэтому нажатие «Отмена» не создаёт бесконечную очередь.
Размер файла не связан ни с числом PSRAM-слотов, ни с числом ожидающих READ.
Внутри запрос по-прежнему делится на физические FILEX-окна по 16 352 байта.
После каждого завершённого окна поле `Copying` получает промежуточное значение;
для размеров от 1 МиБ выводятся сотые доли, поэтому счётчик больше не ждёт
завершения всего 64-КиБ SMB-запроса и не замирает на шагах примерно по 102 КиБ.
Прогресс сервера считается как сумма уникальных успешно переданных диапазонов одного
SMB Open. Поэтому внепорядковые WRITE Windows CopyFile/FAR не откатывают шкалу,
а повторный или перекрывающийся диапазон не учитывается второй раз. Смещение
последнего блока остаётся файловой позицией и больше не используется как число
скопированных байт.
Для клиентской шкалы MaxWrite увеличен с 64 до 512 КиБ. Реальная проверка 0.6.85
показала, что подписанный Windows-сеанс всё равно передаёт WRITE по 64 КиБ и
может менять порядок диапазонов: одного MaxWrite недостаточно. Первый тестовый
образ 0.6.86 с `SecurityMode=0` был отвергнут Windows при NEGOTIATE. В
исправленном образе 0.6.86 сервер правильно объявляет signing доступным, но не обязательным (`SecurityMode=1`),
чтобы Windows мог выбрать неподписанный режим без изменения настроек FAR или
клиента. Аппаратный тест подтвердил `Signed=False`, но Windows по-прежнему
отправлял 64-КиБ WRITE вне порядка смещений. Сервер своевременно отвечал
`SUCCESS, Count=65536`; FAR выводил только `TotalBytesTransferred`, который
системный CopyFile обновлял порциями 512 КиБ. Отдельного поля промежуточного
прогресса в SMB WRITE нет. Любой большой WRITE по-прежнему подтверждается лишь
после фактической записи всех внутренних FILEX-окон и до финала отменяется по
выданному `AsyncId`.
Даже в неподписанном сеансе Windows подписывает контрольный
`FSCTL_VALIDATE_NEGOTIATE_INFO`; сервер сохраняет ключ сеанса, проверяет этот
запрос и подписывает его ответ, не включая подпись для обычных READ/WRITE.
После запуска поле `Status` вместо `Listening` показывает 16-сегментную шкалу
Wi-Fi и точный процент. Это отдельное событие сетевого ядра: `SYS_INFO`, SMB и
FILEX ради индикатора не опрашиваются.
Потерю отдельных сетевых пакетов повторно обрабатывает TCP/lwIP, а Wi-Fi
работает с `setAutoReconnect(true)`. Это не возобновление SMB-сеанса:
Durable/Persistent Handles, перепривязка FileId после нового TCP-подключения и
специальные TCP keepalive/`TCP_USER_TIMEOUT` не реализованы. Уже принятый WRITE
после разрыва дописывается до согласованной границы SD, но клиент продолжить
тот же запрос не может.
При перечислении общих ресурсов `NetrShareEnum` сохраняет отсутствие входного
`ResumeHandle` и возвращает `NULL`, как требует MS-SRVS. Это устраняет цикл
повторных запросов `srvsvc`, из-за которого Проводник зависал на `\\ZX-Evo`.
При копировании SD→SD новый `FILE_CREATE` каталога теперь ставит `STAT` и
`MKDIR` в ту же FIFO-очередь, что READ, WRITE и холодный `QUERY_DIRECTORY`.
Если исходный `FINDNEXT` ещё использует FILEX, Проводник ждёт штатный успешный
ответ вместо ложного «вам необходимо разрешение на выполнение этой операции».
Финальный `CLOSE` также занимает место в этой FIFO и ждёт предшествующий WRITE,
который подтверждается только после физической записи на SD. Версия
`s3-native-0.6.80` устранила
`metadata-not-random`, но аппаратная SD→SD серия выявила ещё один отказ:
последнее неполное окно последовательного FILEX mode=1 подтверждалось до
фактического APPEND, который мог отказать только на CLOSE. В
`s3-native-0.6.81` все SMB WRITE сразу используют random mode=3; каждое окно
физически завершено до ответа WRITE, а `SET_METADATA` применяется в том же
контексте. Mode=1 используется лишь для создания уже закрытого пустого файла.
Отложенные READ, WRITE и холодные QUERY_DIRECTORY передаются под собственный
watchdog приложения: обычный тайм-аут PDU libsmb2 больше не удаляет запрос из
`waitqueue` до прихода позднего ответа от медленного FILEX.
Фиксированное окно из восьми кредитов позволяет принять либо восемь обычных
64-КиБ запросов, либо один multi-credit WRITE 512 КиБ. Восемь PSRAM-слотов
стартуют по 64 КиБ; только выбранный слот динамически растёт до фактической
длины WRITE. Финальный ответ приходит после физического завершения,
поэтому в фоне нет подтверждённого write-back хвоста перед `FLUSH`/`CLOSE`, а
незавершённый WRITE остаётся доступен для точного CANCEL. Заданный Проводником до первой записи
конечный EOF сначала хранится логически: WRITE заполняют файл без отдельного
предварительного расширения нулями, а недостающий хвост создаётся на CLOSE или
FLUSH. Поэтому запись начинается сразу и индикатор получает первые завершённые
порции без паузы на предварительное выделение всего файла. UART принимает
кадры блоками и передаёт payload до 1024 байт одним вызовом. Зависшие операции
останавливает 90-секундный watchdog. Для позиционных операций требуется
`WildCommander Improved/exe/WC/FILEX.WMF` первой активной строкой
`[PLUGINS]`. Готовые параметры — порт `445`,
ресурс `SD`, имя `ZX-Evo`, группа `WORKGROUP`, логин и пароль `zx` / `zx`.
Финальные время и атрибуты, пришедшие во время write-back, сохраняются вместе
с SMB-handle и применяются после данных на CLOSE/FLUSH: SET_INFO не держит
Windows без ответа. Статические FILE_FS_ATTRIBUTE/DEVICE/CONTROL возвращаются
без повторного чтения активной FAT; точный объём и свободное место по-прежнему
берутся из её проверенной копии в PSRAM.

`TREE_DISCONNECT` теперь закрывает все `Open`, принадлежащие отключаемому
`TreeId`, до удаления дерева, как требует MS-SMB2. Каждый `FileId` связан и с
SMB-сеансом, и с конкретным деревом; использовать его через соседнее дерево
нельзя. Прежняя реализация удаляла только запись `Tree`, а открытые дескрипторы
оставляла в общей таблице из восьми слотов. На долгоживущем соединении Windows
повторные подключения исчерпывали таблицу, после чего следующий `CREATE`
каталога получал `STATUS_INSUFFICIENT_RESOURCES`.

`QUERY_DIRECTORY` следует обработке из MS-SMB2 3.3.5.18: неизвестный `Open`
возвращает `STATUS_FILE_CLOSED`, запрос по обычному файлу —
`STATUS_INVALID_PARAMETER`, допустимый, но не реализованный класс —
`STATUS_NOT_SUPPORTED`, а неизвестный класс — `STATUS_INVALID_INFO_CLASS`.
Клиентский максимум ответа ограничен объявленными 64 КиБ. Если
`SMB2_RETURN_SINGLE_ENTRY` не установлен, сервер формирует в этом пределах
список записей MS-FSCC и возвращает точную фактическую длину.

Аппаратный backend Wild Commander имеет один физический курсор каталога, тогда
как Проводник держит несколько независимых SMB `Open`. Поэтому на штатной
ESP32-S3 Zero каталог один раз линейно считывается в ограниченный 512-КиБ
PSRAM-снимок, а каждый `Open` получает собственный логический курсор по нему.
Тот же первый асинхронный проход строит снимок без второго фонового чтения.
Read-only `STAT`/`QUERY_INFO` и переподключение клиента кэш не сбрасывают;
инвалидация происходит только после успешного изменения EVO и только для
затронутого каталога. Физические `READ`, `WRITE` и холодные `QUERY_DIRECTORY`
обслуживаются общей FIFO: более позднее чтение файла не может обогнать уже
ожидающий ответ каталога. Пакетный compound-тест Проводника, обязательные коды
MS-SMB2, регрессия курсора/кэша и проверка FIFO входят в нативный набор из 30
тестов.
Подробная пошаговая инструкция и ограничения текущей версии находятся в
[`SMB Server/README.md`](SMB%20Server/README.md).

## Первая прошивка через USB

Для первоначальной прошивки нового модуля Waveshare ESP32-S3-Zero используется кабель USB Type-C и полный заводской образ [**`firmware.factory.bin`**](firmware/firmware.factory.bin) (записывается со смещения `0x0`).

> [!WARNING]
> **Внимание!** Перед подключением кабеля USB-C обязательно извлеките плату переходника из слота ZX-Evolution (либо отключите питание Спектрума). Источники питания не развязаны.

Подробная пошаговая инструкция со ссылкой на официальный `esptool`, полным
стиранием Flash и обязательным режимом записи `-fm dio` находится в
[`firmware/README_RU.md`](firmware/README_RU.md#первая-установка-через-usb-c).

### Альтернативный способ через PlatformIO

```powershell
pio run -t upload
```

После первой успешной прошивки модуль готов к установке в слот Спектрума, а все последующие обновления выполняются по Wi-Fi.

## Обновление без USB

USB-C нужен только для первой установки `firmware.factory.bin`. После того как
прошивка хотя бы один раз получила `WIFI_INI` от совместимой Native-программы,
полный `zifi.ini` сохранён в LittleFS и сеть восстанавливается после reset.

Для обычного пользователя предназначен `Online Update/build/ZIFIUPD.WMF`:

1. Один раз установите прошивку `s3-native-0.6.69` или новее прежним способом,
   поскольку более старые версии ещё не поддерживают раздельные команды проверки
   и установки.
2. Скопируйте `ZIFIUPD.WMF` в `/WC` и запускайте его из меню плагинов Wild
   Commander. Файл `/zifi/zifi.ini` должен содержать действующие параметры Wi-Fi.
3. Плагин без записи во Flash покажет `Current`, `Available` и результат
   сравнения. Нажмите `Enter` для установки. При `Same version` Enter выполняет
   восстановительную переустановку того же опубликованного образа.
4. ESP сама загрузит по проверяемому HTTPS сначала `firmware.sha256`, затем
   `firmware.bin` из GitHub `main`, сверит полный SHA-256, переключит неактивный
   OTA-слот и перезапустится. PC, IP-адрес и Python пользователю не требуются.

До совпадения SHA-256 текущий загрузочный слот не меняется. При обрыве,
неверном образе или ошибке записи вызывается `Update.abort()`. После успешного
перезапуска плагин повторно читает `SYS_INFO` и показывает запущенную версию.

Актуальный пользовательский плагин можно
[скачать как `ZIFIUPD.WMF` напрямую с GitHub](https://github.com/andrewinsidelazarev/ZiFi-ESP32-S3-Zero/raw/refs/heads/main/Online%20Update/build/ZIFIUPD.WMF).
Подробный порядок первой USB-прошивки и последующих обновлений через GitHub
описан в [`firmware/README_RU.md`](firmware/README_RU.md).

## Аппаратное предупреждение

Переходник подаёт 3,3 В основной платы непосредственно на контакт `3V3`
ESP32-S3-Zero. Нельзя подключать USB-C, пока переходник установлен в запитанную
основную плату: источники питания не развязаны.

Параметры модуля и рекомендация PlatformIO:
[Waveshare ESP32-S3-Zero](https://www.waveshare.com/wiki/ESP32-S3-Zero).
