# Индикатор копирования FAR/Windows CopyFile: 0.6.84–0.6.86

## Наблюдение

При успешном копировании `ZUMALVL.PAK` размером 7 139 840 байт с ПК на EVO
поле `Copying` ходило назад и после 100% в FAR показало
`DONE 5.00M/6.80M`.

Захват `far_zumalvl_reverse_0683_20260828-232038.pcapng` подтвердил 103
попавших в трассу WRITE и 103 успешных финальных ответа. Запросы пришли не по
порядку логических смещений: в трассе было пять возвратов назад. Последний
WRITE имел смещение 5 177 344 и длину 65 536, то есть заканчивался ровно на
5 242 880 байтах (5,00 МиБ). Старый индикатор выводил этот конец последнего
блока как скопированный объём, хотя FAR уже передал весь файл.

Это не сортировка по LBA внутри FAR. В проверенной сборке FAR включён штатный
`UseSystemCopy`, поэтому копирование выполняет Windows `CopyFileEx`; порядок
SMB WRITE задаёт системный кэш и SMB redirector.

## Исправление

Для каждого SMB Open прошивка отдельно хранит отсортированное объединение
успешно завершённых диапазонов `[offset, offset + length)`. Значение индикатора
равно сумме длин объединённых диапазонов.

- блоки могут завершаться в любом порядке, но значение не уменьшается;
- повторный или перекрывающийся диапазон не считается дважды;
- короткий последний блок учитывается по фактической длине;
- READ и WRITE имеют раздельные сеансы прогресса;
- `QUERY_INFO` и команды другого файлового дескриптора счётчик не меняют;
- файловая `position` сохраняет прежнюю протокольную роль, но не используется
  как число скопированных байт.

Диапазоны выделяются по мере необходимости из PSRAM с резервным выделением из
обычной 8-битной кучи. При закрытии, отключении клиента или дерева память
освобождается. При усечении файла диапазоны обрезаются до нового EOF.

## Регрессия

Host TEST 36 создаёт файл 320 КиБ и пишет блоки 64 КиБ в порядке
`192K, 0, 64K, 0, 128K, 256K, 192K`. Два диапазона повторяются, а последний
WRITE заканчивается на 256 КиБ.

Ожидаемый итог:

```text
[COPYING] DONE 320.0K/320.0K
```

Runner дополнительно проверяет все 327 680 байт файла по детерминированному
шаблону. Старый алгоритм дал бы `256.0K/320.0K`, простой счётчик блоков —
`448.0K/320.0K`.

## Клиентская шкала и тайм-аут SMB 0.6.85

Повторный успешный захват
`captures/far_progress_0684_20260829-002925.pcapng` содержит 109 WRITE на файл
7 139 840 байт: 108 по 65 536 байт и последний 61 952 байта. Windows сначала
отправил offset 0, затем первые 64 КиБ последующих 512-КиБ порций, и лишь позже
заполнил пропуски 64K..512K. Поэтому клиентская шкала стояла на 0%, затем
прыгнула на 7% и 66%; это был порядок SMB redirector, а не LBA-сортировка FAR.

Прошивка 0.6.85 объявляет MaxWrite 512 КиБ и окно из восьми credits. Одна порция
CopyFile теперь остаётся одной SMB WRITE-командой и только внутри сервера
делится на окна FILEX. Успешный ответ всё равно приходит после физической
записи, поэтому исправление шкалы не создаёт скрытого write-back.

Тот же захват показал задержку финального WRITE до 59,76 секунды при отсутствии
TCP reset, FIN, zero-window и повторных TCP data segments. Это почти совпадает с
обычным 60-секундным сроком Windows SMB file I/O и объясняет, почему на более
слабом Wi-Fi SMB обрывается, хотя потоковый FTP продолжает передачу.

512-КиБ WRITE сразу получает `STATUS_PENDING`; остальные асинхронные READ/WRITE
получают его после 30 секунд. Interim не подтверждает данные, а продлевает срок
запроса Windows. Перед ним сервер снижает credit target до одного. Поэтому
клиент не подпитывает очередь новым запросом за каждый PENDING, а `CANCEL`
адресуется по `AsyncId`. После финала target возвращается к восьми.

Локальный host-набор TEST 1–31, отдельные TEST 32–39 и проверки
тайм-аут/FIFO/CLOSE прошли. TEST 37 проверяет единственный 512-КиБ WRITE и
побайтный read-back; TEST 38 — PENDING, CANCEL по AsyncId и credits 1→1→8;
TEST 39 — медленный READ, один AsyncId, финальный нулевой credit и точные 65 536
байт.

Аппаратная проверка 0.6.85 на EVO 29 августа показала, что одного
`MaxWrite=512 KiB` недостаточно. Сервер действительно отдал в живом NEGOTIATE
`Capabilities=0x44` (`LARGE_MTU` включён) и `MaxWrite=524288`, а клиентская
настройка Windows `EnableLargeMtu=True`. Несмотря на это, подписанный сеанс
Windows Server 2022 (`Signed=True`) продолжил отправлять WRITE по 65 536 байт.
В 25-секундном фрагменте реального FAR были финальные ответы примерно через
10 секунд на блок и отдельный `STATUS_PENDING` после 30 секунд; TCP reset,
повторной передачи и ошибки SMB не было. Следовательно, прежнее утверждение,
что один увеличенный MaxWrite исправит клиентскую шкалу, аппаратно не
подтвердилось.

## Ошибка первого образа и исправленный 0.6.86

Samba-эталон на том же Windows работал без signing, тогда как ZiFi одновременно
объявлял и принудительно требовал signing, хотя локальная политика клиента его
не требует (`RequireSecuritySignature=False`). Попытка 0.6.86 вообще не
объявлять signing дала `SecurityMode=0`: сырой probe его принимал, но Windows
отверг NEGOTIATE с системной ошибкой 8. По MS-SMB2 сервер обязан выставлять
`SIGNING_ENABLED`.

В исправленном бинарнике 0.6.86 сервер возвращает `SecurityMode=1`: signing
доступен, но не требуется. Настройки FAR и Windows не меняются.

Первый вариант с `SecurityMode=1` дошёл до неподписанного сеанса, но Windows
завершил подключение с `NTE_BAD_SIGNATURE`: контрольный
`FSCTL_VALIDATE_NEGOTIATE_INFO` обязан иметь корректную подпись даже при
необязательной подписи остального сеанса. Исправленный сервер сохраняет signing
key, проверяет подписанный запрос и подписывает только его ответ. Host-регрессия
проверяет `SUCCESS` и `SMB2_FLAGS_SIGNED`.

Финальный аппаратный тест установил рабочий сеанс SMB 3.0.2 с `Signed=False`.
Несмотря на `MaxWrite=524288`, Windows продолжил отправлять WRITE по 65 536
байт и менять порядок смещений. В захваченном фрагменте каждый запрос примерно
через секунду получал `STATUS_SUCCESS` и `Count=65536`: сервер не задерживал
информацию о завершённом WRITE. FAR напрямую выводит `TotalBytesTransferred`
из системного CopyFile и обновлялся на 524 288, затем на 1 048 576 байтах,
пока серверный индикатор уже показывал фактически записанные внепорядковые
диапазоны. Следовательно, optional signing исправил подключение Windows, но не
частоту системного callback; отдельного промежуточного прогресса SMB WRITE не
предусматривает.
