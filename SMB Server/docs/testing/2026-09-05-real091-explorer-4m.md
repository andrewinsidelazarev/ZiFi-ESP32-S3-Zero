# Реальный ZX-Evo: отставание индикатора Explorer после 4 МиБ

Статус: дефект индикатора НЕ закрыт. Запись дошла до успешного CLOSE; полное
обратное чтение через SMB подтвердило SHA-256 оригинала. Это не доказывает
корректную шкалу Explorer.
Все времена ниже — 2026-09-05, UTC+02:00.

Позднее выполнен отдельный полный прогон с Windows Kernel-File ETW:
[сопоставление IRP, SMB и шкалы Explorer](2026-09-05-real091-explorer-fileio.md).
Он подтверждает именно паузы индикатора при продолжающемся копировании.
Условия и результаты двух прогонов не смешивать.

## Условия и границы наблюдения

- Windows `192.168.1.50`, Explorer PID 9984, настоящий ZX-Evo
  `192.168.1.113:445`, клиентский TCP-порт 63514. SMB 3.0.2, ресурс `SD`.
- Копию запустил пользователь. Ассистент её не запускал повторно, не отменял,
  не приостанавливал и не перезапускал Explorer, SMB или ESP.
- Файл: `Desktop/20260629-10-16-08.jpg`, 7 872 598 байт; назначение
  `\\ZX-Evo\SD\111\20260629-10-16-08.jpg`.
- Источник SHA-256:
  `8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B`.
- Образ из предшествующего OTA-шагa: `s3-native-0.6.91`,
  `firmware/firmware.bin`, 1 168 928 байт, SHA-256
  `B10F0FFEF2821CAAD5C8C0DD8B1F67A268B121F10EF4A9A9533D9A9C52781FB5`.
  Локальный бинарник повторно проверен; чтение образа из flash здесь не выполнялось.
- Запасной HIL ESP оставлен вне Wi-Fi; COM4/COM5 не открывались.
- Пользователь подтвердил, что счётчик Copying на настоящем ZX-Evo продолжал
  расти, пока шкала Windows стояла. Это отдельное наблюдение от ответа SMB.
- Захват начат уже во время плато. Начало копии, NEGOTIATE и переход через
  первые 4 МиБ этим захватом не покрыты. Его нельзя называть полным прогоном.
- Во время записи индикатор читался через UIAutomation, без дополнительных
  открытий копируемого файла. Обратное чтение начато только после CLOSE.

## Что было на проводе

На протяжении захваченного участка сохранялся тот же TCP-сеанс. Получены
30 успешных файловых WRITE-ответов: 29 по 65 536 байт и хвост 8 278 байт,
всего 1 908 822 байта. Два первых запроса отправлены до начала захвата;
их ответы нельзя использовать для восстановления конкретных диапазонов файла.
Оставшиеся запросы имеют FileId `5a534d42c467bdf3020000003b98420c`.

Новые WRITE не прекращались при неподвижном индикаторе. Windows отправлял
следующие запросы сразу после успешных ответов, перемежая разные смещения.
Примеры из одного и того же открытого файла:

У последних запросов время от запроса до ответа около 25 секунд: в работе
обычно видны два ожидающих WRITE, а очередной финальный ответ приходит примерно
раз в 12–13 секунд. Это измерение SMB, не непосредственное измерение скорости SD.

**FLUSH в трёх захватах нет вообще.** Нет и ошибки файлового WRITE или CANCEL.
Последний WRITE, MID 562, завершился в 07:41:23.488. CLOSE основного FileId,
MID 575, получил SUCCESS в 07:41:23.644 с EOF 7 872 598 байт.

После данных Windows пытался создать `:Zone.Identifier`, получил
`STATUS_OBJECT_NAME_INVALID` и продолжил завершение. Это отдельное ограничение
альтернативных потоков, а не ошибка передачи основного содержимого JPG.

## Контроль старого HIL25: почему прежняя приёмка была недостаточной

Заново разобраны полный
`C:\zifi-0689-hil25-final-explorer-6m.pcapng` (TCP/60384) и
`C:\zifi-hil25-final-explorer-progress.log`. Это реальный ESP/SMB/UART с
эмулятором файлового тракта, НЕ SD-карта настоящего ZX-Evo.

В этом прогоне все 96 WRITE по 64 КиБ успешно завершились. До 4 МиБ запросы
шли по возрастанию смещения. После последнего из них, MID 91, Windows открыл
служебный metadata-only handle (MID 92), затем отправил WRITE со смещениями
5,5 МиБ, 4,5 МиБ, 4 МиБ, 5 МиБ и стал перемежать их продолжения.

Сопоставление UI со СУММОЙ УНИКАЛЬНЫХ подтверждённых диапазонов:

| Время | UI | Подтверждено SMB | Сумма целиком завершённых групп по 512 КиБ |
| --- | ---: | ---: | ---: |
| 04:03:43.548 | 65% | 4 194 304 | 4 194 304 |
| 04:05:26.631 | 74% | 5 308 416 | 4 718 592 |
| 04:06:21.238 | 90% | 5 898 240 | 5 767 168 |
| 04:06:57.630 | 99% | 6 291 456 | 6 291 456 |

Между 65% и 74% — 103,083 секунды. За это время подтверждены ещё
1 114 112 байт, но лишь одна новая 512-КиБ группа завершена целиком. Поэтому
запись `0..99%, окно закрылось` НЕ доказывала отсутствие плато после 4 МиБ.
Старый отчёт о решённой проблеме индикатора был чрезмерным.

Поле BACKING старого журнала — размер файла, а не сумма записанных диапазонов.
При непоследовательных WRITE оно растёт до максимального смещения и завышает
представление о завершённости; PHYSICAL_PERCENT, вычисленный из него, не является
достоверным счётчиком передачи. Для сравнения выше используется PCAP, не EOF.

Отдельно пересчитаны кредиты полного HIL-захвата: выданные в ответах кредиты
минус CreditCharge новых запросов, без повторов compound-заголовков. После
MID 56 (04:00:11.053) окно снова расширилось до 8. Перед metadata CREATE на
4 МиБ у клиента было 8 свободных кредитов; при двух дальнейших WRITE оставалось
6. Следовательно, два параллельных запроса на этом участке нельзя объяснять
«окно сервера застряло на одном кредите». Один CreditResponse в очередном
ответе не означает, что весь доступный клиенту бюджет равен одному.

На Windows при диагностике прочитаны, но НЕ изменены параметры:
`EnableBandwidthThrottling=True`, `EnableLargeMtu=True`, `MaxCmds=50`,
`WindowSizeThreshold=1`, `SessionTimeout=60`. Microsoft описывает
[влияние SMB bandwidth throttling на высоколатентные соединения](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/file-server/).
Это только возможное условие для отдельного контрольного сравнения, а не
установленная причина данного плато. Глобальные настройки Windows ради этого
наблюдения не менялись.

## Вывод и оставшаяся работа

Для регрессионного ориентира повторно разобран и старый реальный захват
`SMB Server/docs/captures/lease_progress_0689_20260901_234001.pcapng` из основного
checkout. В потоке TCP/57894, FileId `5a534d42b48c6db3020000004b73924c`,
действительно находятся 121 строго последовательный WRITE общим размером
7 872 598 байт: 120 полных блоков и хвост 8 278 байт. Все 121 запроса получили
SUCCESS; у 13 был промежуточный PENDING. Медиана request-to-final — 23,241 с.
Это проверенный пример другого поведения ранней `.89`, а не доказательство,
что простое обратное включение lease в изменённой `.91` устранит регрессию.

1. В данном наблюдении зависла не вся передача: сохранялись успешные WRITE,
   рос счётчик ZX-Evo, затем произошёл успешный CLOSE.
2. Шкала Explorer отстаёт от уже подтверждённых 64-КиБ SMB WRITE. Наблюдаемая
   картина согласуется с ожиданием завершения более крупных порций CopyFile,
   перемежающихся после 4 МиБ. Это вывод из трассы, а не измерение внутренних
   переменных Copy Engine: отдельный callback/ETW в данном прогоне не снимался.
3. Отключение lease в HIL25/нынешней `.91` не устранило этот сценарий.
   Изменение только FLUSH не исправит участок, на котором FLUSH не отправлялся.
4. Функциональная правка прошивки в рамках этого наблюдения не выполнялась;
   причина выбора Windows именно такого порядка и проверенное серверное
   исправление пока не установлены. Нельзя объявлять `.91` исправленной.
5. Следующая проверка индикатора должна начинаться ДО копии: один и тот же файл
   больше 4 МиБ, видимый Explorer, полный wire-захват, интервалы плато и сумма
   уникальных успешных WRITE. Менять по одному условию, сохраняя честный SUCCESS
   после физической записи, отмену и обслуживание второго клиента.

## Обратное чтение

После копии запущен `tools/host_smb/verify_remote_file_readonly.ps1`:
новый FileStream/Open только для чтения, SHA-256 всего файла против локального
оригинала. Прямое имя по IP не имело подходящих Windows credentials; настройки
входа не менялись, проверка использует уже аутентифицированное имя `ZX-Evo`.
TCP к настоящему устройству `.113` подтверждён отдельно.

Вспомогательный скрипт дополнительно проверен на двух локальных файлах:
одинаковые данные дают `match=True` и код 0, разные — `match=False` и код 1.
Оба диагностических PS1 прошли синтаксический разбор PowerShell. Это тесты
инструментов наблюдения, не host-регрессия прошивки и не доказательство записи SD.

Полная проверка завершилась успешно около 08:11:21, код процесса 0:

```text
RESULT match=True bytes=7872598
sha256=8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B
elapsed_s=1477.1
```

Это PASS содержимого данной копии при обратном чтении через SMB. Оно заняло
24 мин 37 с. Во время проверки не создавались новые файлы на ZX-Evo.
Новый FileId чтения — `5a534d42d767bdf3040000002898420c`. В захвате есть
123 успешных READ, объединение их диапазонов точно равно `[0, 7872598)`.
Всего сервер передал 7 934 124 байта, включая перекрывающиеся чтения Windows;
это не 7 934 124 уникальных байта и не размер файла.
Совпадение SHA через SMB не является независимым чтением вынутой SD-карты
и не доказывает сохранность после внезапного отключения питания.

## Артефакты

PktMon: существующий фильтр TCP/445, `--comp nics --pkt-size 0`. При остановке
каждого захвата — нет потерянных событий; конвертация PCAPNG без отброшенных пакетов.
Сетевой offload всё равно требует осторожности: для заголовков использован
`analyze_smb_pcap.py --scan`, а не вывод об обрыве по дырке в TCP-reassembly.
Повтор compound-члена при `--scan` в существующем парсере не считать повтором
команды клиента. Для счётчиков заголовки дедуплицированы по направлению,
TCP-позиции, команде, MessageId и статусу.
