# Реальный Evo: обрыв WRITE около 3,53 МиБ, 2026-09-05

Это **неуспешное копирование**, отдельно от прежних зависаний только индикатора.
Пользователь сообщил `0x80070079` в Windows и оборванный WRITE на `3,53М`
на самом Evo. Полной копии и независимой проверки содержимого SD нет.

  `B10F0FFEF2821CAAD5C8C0DD8B1F67A268B121F10EF4A9A9533D9A9C52781FB5`.

  SHA-256 `8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B`.
- Новый целевой файл `\\ZX-Evo\SD\111\EVO2125.JPG`; видимый Explorer CopyHere,
  запуск `21:25:13.1585518+02:00`. Файл не удаляли, Retry/Cancel не нажимали.
- Артефакты: `C:\zifi-evo-20260905-2125`. Основные: `ui.log`, `copy.log`,
  `second-client.log`, `failure-client-events-full.xml`,

- Основной PCAP: 989 110 байт; SHA-256
  `15F4B10F2289E4BDB41DFD940D4248F0B5BD0D337349100FE5F8878758DB5E91`.

  `smb-full-failure.pcapng` **не является полным**, несмотря на имя.

## Что видно на проводе

Ниже местное время UTC+02. SMB FileId:
`5a534d421668bdf302000000e997420c`; каждый запрос — 65 536 байт.

| MID | Смещение | Запрос | Ответ |
| --- | ---: | --- | --- |
| 92 | 3 604 480 | 21:34:19.057 | SUCCESS 65 536 в 21:34:39.015 |
| 93 | 3 670 016 | 21:34:29.046 | PENDING в 21:34:59.294, AsyncId 17; IO_TIMEOUT лишь в 21:38:24.946 |
| 94 | 3 735 552 | 21:34:39.015 | Без PENDING; IO_TIMEOUT лишь в 21:38:24.962 |
| 95 | 3 801 088 | 21:34:59.294 | Без PENDING; IO_TIMEOUT лишь в 21:38:24.962 |

Последний успешный WRITE заканчивается на **3 670 016 байтах = 3,50 МиБ**.
Последующие три ответа — `STATUS_IO_TIMEOUT (0xC00000B5)`, **не успех**.
TCP-повторы этих поздних ответов не являются новыми SMB-завершениями.

ESP подтвердил TCP-приём последнего запроса в `21:34:59.578`.
В `21:35:29` и `21:35:59` отвечал на keepalive. Windows отправила RST в
`21:36:09.152`; SMBClient записал DeviceTimeout (30823/30805/30807).
`ui.log` фиксирует ошибку `0x80070079: Превышен таймаут семафора` в
`21:36:12.634`, индикатор оставался около 46%.

Таким образом, сетевой стек отвечал, но завершения SMB WRITE перестали
приходить вовремя. Почему ESP позднее ещё передавал ответы по старому TCP,
отдельно не установлено. Ошибка DNS в 21:36:11 появилась **после** тайм-аута;
оснований объявлять её причиной исходного обрыва нет.

`3,53М` на Evo согласуется с двумя дополнительными окнами по 16 КиБ внутри
следующего WRITE: 3,50 + 0,03125 МиБ. Это интерпретация округлённого индикатора,
**не измерение реально записанного на SD диапазона**. Одно окно моста 16 КиБ
в FILEX mode=3 передаётся частями 16 352 + 32 байта, поэтому показание не
указывает, какая именно часть или её ACK пропали.

Второй независимый клиент в 21:29:03–21:29:07 перечислил `111`: 4 записи,
OPEN 3266 мс, enumerate 0 мс, CLOSE 0 мс, ECHO 16 мс, PASS. Это проверка
параллельного листинга **до** остановки FILEX, не во время неё.

CopyHere вернулся в `22:01:49.313`; это не признак успешной копии.
При последующей проверке процесс уже отсутствовал. Агент его не завершал;
способ закрытия диалога по имеющимся журналам не установлен.

## Найденный дефект и граница вывода

В исходном `failAsyncWrites` сначала выполняется блокирующий
`bridge.reclaim(kMutateVfsTimeoutMs)` (до 190 секунд), и только потом
ставятся ответы об ошибке. Далее `closeActive(false)` также синхронный.
Это задерживает сетевую задачу и обслуживание других SMB-клиентов.

Отдельный минимальный тест в `C:\zifi-reclaim-20260905-2157` воспроизвёл
этот дефект на том же C++/libsmb2-коде: watchdog специально укорочен до 500 мс,
FILEX-ответ задержан на 3 секунды начиная со смещения 32 КиБ. Исходный код:
все три ошибки WRITE через 6312 мс, второй ECHO задержан на 1343 мс, FAIL.
Первый вариант неблокирующей уборки: ошибки WRITE через 813 мс,
оба ECHO без измеримой задержки, PASS. Продолжение тестов записывается отдельно.

Это **доказательство дефекта обработчика ошибки**, но не причина первой
потери прогресса FILEX на реальном Evo. Нет UART-трассы именно реального
`.113`; COM4/COM5 относятся к запасному ZX-Test. Нельзя выдавать его журнал
за журнал физического плагина, FAT или SD на Evo.

Отдельно остаются: исходная остановка FILEX, PENDING для долго ожидающих
WRITE без переполнения восьми PSRAM-слотов и задержки индикатора Explorer.
Изменение reclaim само по себе не доказывает устранение этих проблем.

## Исправленный обработчик и завершённые проверки

Изменения перенесены из изолированного контроля в рабочие исходники:

- `src/smb_server.cpp`: немедленный финальный ответ об ошибке, сохранение
  активного слота/ownerId до возврата окна; затем неблокирующий CLOSE_ABORT.
  Поздний ACK не подтверждает успех и не запускает повторную запись.
- После финальной ошибки WRITE в тот же FileId отклоняется. После TCP-close
  восстановление ошибочного WRITE не превращается в обычную допись.
- Ошибке уже отвеченного WRITE не посылается поздний PENDING. Watchdog READ
  не забирает мост у активного WRITE только из-за наличия ожидающих READ.
- Восемь слотов, MaxWrite 64 КиБ, обычные credits и аппаратный watchdog
  **90 секунд** сохранены. Короткий watchdog доступен лишь PC-сборке через
  `ZIFI_HOST_BUILD` + `ZIFI_HOST_ASYNC_WATCHDOG_MS`.

Специальные регрессии: три WRITE по 64 КиБ; задержка каждого FILEX-окна
3 секунды после первых 32 КиБ; дополнительно CLOSE_ABORT задержан на 3 секунды.
Проверяются точные коды ошибок, отсутствие повторного финального ответа,
отказ нового WRITE после ошибки, пять ECHO второго клиента, перечисление
каталога, разрыв TCP записывающего клиента и запись/чтение нового файла 4096 байт.

Последний запуск из рабочей папки:
`.test-build/reclaim-recovery/final-local-path-2234/probe.log`:

- WRITE: по одному IO_TIMEOUT через 1469 мс от старта;
- повтор после ошибки: IO_DEVICE_ERROR, задержка 0 мс;

- каталог второго клиента: SUCCESS после ожидания FILEX, 8422 мс;

### Повтор специального PC-теста

Из корня рабочего дерева, **только локальный сервер**, не адрес Evo:

```powershell
.\tools\host_smb\build.ps1 -ServerOnly -AsyncWatchdogMs 500
.\tools\host_smb\build_reclaim_probe.ps1
.\tools\host_smb\run_reclaim_probe.ps1 -AbortDelayMs 3000 -Disconnect
```

Скрипт создаёт уникальную папку внутри `.test-build/reclaim-recovery`,
слушает только тестовый SMB-порт 14457 и завершает лишь собственный сервер.
Существующие профили не перезаписывает. `-ServerBinary` позволяет выбрать
сохранённую PC-сборку; нельзя передавать вместо неё прошивочный `.bin`.
После опыта обычная сборка без `-AsyncWatchdogMs` возвращает 90 секунд.

Эти результаты доказывают PC-обработку тайм-аута и компилируемость ESP,
**не аппаратное устранение обрыва на 3,53М**. Ни ZX-Test, ни реальный Evo
этим образом пока не прошиты.
