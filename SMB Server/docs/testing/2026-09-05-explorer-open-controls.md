# Explorer: служебный OPEN, очередь WRITE и скачок индикатора

## Статус и границы

Исправление индикатора **не получено**. Ни один вариант из этой серии не
перенесён в исходники основной прошивки или на ESP. Реальный ZX-Evo не
перезапускался и не прошивался. Defender и его исключения не менялись.

Каталог опытов: `C:\zifi-open-20260905-2007`. Это отдельная ASCII-копия
`.test-build/origin_0689_worktree`, а не основной native-rewrite в корне проекта.
В экспериментальном `src/smb_server.cpp` стоит запрет сборки без
`ZIFI_HOST_BUILD`. Очередь на 4 МиБ **не помещается в 2 МиБ PSRAM ESP**.

Путь контроля: настоящий Windows Explorer / CopyHere -> Windows SMB 3.0.2 ->
изолированный мост WinDivert -> native-сервер -> FILEX-эмулятор -> backing-файл
на ПК. Это **не HIL**, не испытание Wi-Fi/UART и не запись SD на ZX-Evo.
Для каждого опыта использовался отдельный виртуальный IP и новый файл.
Мост слушал только выбранный адрес:445 и перенаправлял его на 127.0.0.1:14456.

Все исходные JPEG в этой серии: 7 872 598 байт, SHA-256
`8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B`.
Лимит FILEX-эмулятора — 65 536 байт/с; фактическая скорость ниже из-за накладных
расходов. CopyHere запускался видимым процессом, наблюдатель UI и PCAP — до копии.

## Выполненные контроли

Все варианты этой таблицы сохраняли MaxWrite = 65 536 байт.
`PENDING всех` означает: один промежуточный ответ для каждого принятого WRITE,
достигшего порога 30 с, включая ожидающий физического обслуживания запрос.

| Профиль / последний октет IP | Очередь / credits | Изменение | Результат |
| --- | --- | --- | --- |
| `open-rh` / .95 | 8 / 512 КиБ | Lease RH; PENDING только активного после 30 с | SHA совпал; плато 26% и 52% осталось |
| `open-pending250` / .96 | 8 / 512 КиБ | Lease NONE; PENDING активного после 250 мс | 121 PENDING, SHA совпал; плато 52% осталось |
| `open-ordered64` / .97 | 64 / 4 МиБ | Приоритет меньшего offset одного Open; PENDING только активного | **Внесённая экспериментом ошибка 0x8007003B**, тайм-аут ожидающих WRITE |
| `open-ordered64-pending-all` / .98 | 64 / 4 МиБ | Тот же приоритет; PENDING всех | Один проход без длинного плато, SHA совпал; непригодно для памяти ESP |
| `open-ordered16-pending-all` / .99 | 16 / 1 МиБ | Тот же приоритет; PENDING всех | SHA совпал; плато 52% и 72% вернулось |
| `open-no-multicredit8` / .100 | 8 / 512 КиБ | LARGE_MTU выключен, сортировки нет; PENDING всех | SHA совпал; плато 52% осталось |
| `open-rwh8` / .101 | 8 / 512 КиБ | LARGE_MTU возвращён, lease RWH, сортировки нет; PENDING всех | SHA совпал; плато 52% почти минуту, затем скачок в конце |

Ни RH, ни RWH в этих опытах не являются готовой реализацией lease: автомат
отзыва кэширования при конфликтующем втором клиенте не реализован. Нельзя
переносить диагностическую выдачу LeaseState=7 в прошивку или использовать с
чужими данными. Простое разрешение кэширования проблему не устранило.

Отключение LARGE_MTU — также не кандидат на выпуск. Помимо неудачного результата,
[MS-SMB2, Receiving an SMB2 NEGOTIATE Request](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/b39f253e-4963-40df-8dff-2f9040ebbeb1)
требует SupportsMultiCredit для SMB 2.1/3.x поверх TCP 445. Ограничение размера
WRITE величиной 64 КиБ само по себе не отменяет это требование.

## Ошибка опыта .97 — установлена по журналу клиента

Исходное соединение копии: клиентский TCP-порт **59415**. Порт 59434 принадлежит
последующему переподключению и не подходит для анализа причины обрыва.

Windows приняла 43 успешных ответа из первых 64 WRITE. Часть остальных запросов
осталась в очереди без ответа примерно 69,7 с. В SMBClient/Connectivity:

- 30809: WRITE, в том числе MessageId 0x58, ElapsedTime около 69 729 мс;
- 30823: соединение закрыто из-за тайм-аутов операций;
- в PCAP исходного соединения — клиентский RST в 20:26:23.816 (UTC+02).

Это не доказательство плохого Wi-Fi и не ошибка реальной прошивки, вызванная
этим запуском: опыт был на ПК. Увеличить очередь, оставив PENDING только у
обслуживаемого WRITE, оказалось ошибкой. Опыт .98 с PENDING ожидающих запросов
завершился без этого тайм-аута; это не доказательство безопасности такого
изменения при восьми PSRAM-слотах. Ранее .hil22 уже переполнял их при возврате
credits через PENDING. Нужна отдельная проверка бюджета памяти и credits.

После сохранения `ordered64-client-events.xml`, PCAP и
`ordered64-error-dialog.txt` собственная ошибочная копия отменена кнопкой
«Отмена» в 20:41:17. Возврат CopyHere после этой отмены **не является успехом**.
Снимок исходников и бинарника: `ordered64-before`.
Правильный разбор PCAP: `open-ordered64-failed-connection`, не разбор reconnect.

## Последний скачок скорости: open-rwh8

Источник: `source\open-rwh8.jpg`; назначение:
`\\198.18.0.101\SD\files\open-rwh8.jpg`; клиентский TCP-порт 60498.
Начало CopyHere 21:11:09.085, последний WRITE SUCCESS 21:13:37.349,
возврат CopyHere 21:13:37.491, окно отсутствует с наблюдения 21:13:38.741.
Время здесь UTC+02, в CSV SMB — UTC.

По полностью собранному TCP-потоку: 121 WRITE SUCCESS, 7 872 598 байт,
объединение диапазонов строго `[0, 7872598)`, 0 WRITE PENDING, 0 ошибок WRITE,
0 FLUSH, 0 CANCEL. Полный SHA исходника и backing-файла совпал.

| Наблюдение UI | Успешно записано уникальных байт | Непрерывный записанный префикс |
| --- | --- | --- |
| 21:12:30.265, 52% | 4 259 840 | 4 194 304 |
| 21:13:29.503, 66% | 7 413 846 (около 94% файла) | 5 308 416 |

В последнюю минуту последовательные 10-секундные окна давали по SMB WRITE
SUCCESS 51,2; 52,01; 51,2; 51,2; 51,2; 57,6 КиБ/с. Последние восемь ответов
на полные 64-КиБ WRITE шли примерно раз в 1,22 с — резкого ускорения записи нет.
Самый последний WRITE записывал offset 5 701 632, а не конец файла: более
поздние участки уже были записаны ранее.

Вывод из трассы: скачок UI отражает запоздалый учёт уже выполненной работы,
а не ускорение передачи. Удержание процента до заполнения ранних пропусков
согласуется с наблюдениями. Точная формула скорости Explorer и его внутренние
progress-callback в этом опыте не перехватывались; утверждать их реализацию
по одному тексту окна нельзя. Это оставшийся дефект индикации, а не успех опыта.

## Инструменты и сохранённые артефакты

- PCAP, `*-copy.log`, `*-ui.log`, `*-server.log`, `*-server.err`,
  `*-processes.json` сохранены в каталоге опытов. Захваты могут содержать
  содержимое файлов и SMB-аутентификацию; не публиковать открыто.
- `correlate_explorer_fileio.py` теперь собирает TCP-поток перед разбором SMB:
  разделённые заголовки, повторные сегменты и compound больше не считаются
  потерянными командами. Старый разбор `open-rh` пропускал два WRITE; правильный
  результат — 121 SUCCESS в `open-rh-reassembled`.
- `test_trace_transport.py`: 9 тестов PASS. Это проверка анализатора, не сервера.
- Наблюдатель UI распознаёт «действие прервано», пишет ATTENTION и возвращает
  ошибку вместо прежнего ложного «окно исчезло — успех». Он ничего не нажимает.
- Полная host-регрессия и новый HIL в этой серии не выполнялись. Сборка
  экспериментального native-сервера не подтверждает работоспособность ESP.
