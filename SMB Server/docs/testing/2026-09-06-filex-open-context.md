# Повторное использование FILEX-контекста при позиционной записи

## Изменение

`activateWrite` больше не закрывает и не открывает тот же физический файл
только из-за нового смещения SMB WRITE. Уже активный random-контекст того же
FileId сохраняется в ESP. `VfsBridge::kWriteAt` по-прежнему вызывает
`VfsClient::seekFile` перед каждым окном; абсолютное позиционирование не
отключалось. Для другого FileId либо другого режима физическое переключение
остаётся обязательным.

Служебные SMB OPEN/QUERY/CLOSE только для метаданных уже используют таблицу
открытых объектов ESP и не должны менять этот физический контекст.

Это устранение лишних операций, **не доказанное исправление индикатора**.

## Проверка на ПК

TEST 47 пишет восемь блоков по 64 КиБ в порядке `0,4,1,5,2,6,3,7`.
Между блоками выполняются metadata OPEN, запрос нормализованного имени и CLOSE.
После закрытия пишущего FileId файл открывается для контрольного чтения.

## Отдельная проверка SMB CANCEL

Первый запуск нового TEST 48 в 00:33:39 не дошёл до отправки WRITE/CANCEL:
создание файла не удалось. Обнаружено отсутствие FILEX-помощника и его
родительского окна; прежний UART-журнал остановился в 00:32:44. Причина
завершения процессов не установлена. Это произошло после отмены Explorer
и не объясняет её задержку. `hil\cancel-probe.log` — НЕ PASS CANCEL.

В 00:39:17 запущен видимый RDP-overlapped attach к тому же COM4/backing,
без WIFI_INI/SYS_INFO/SMB_START и без прошивки ESP. Исходник помощника:
`C:\zifi-openctx-20260905-2350\attach_rdp.cpp`; сборка завершилась с кодом 0.
ServerGuid после attach не изменился: `d435ab4ec8a8564089882e2acb92c1e7`.

Повторный TEST 48 завершён 00:39:59: отмена одного WRITE 65536 байт
по MessageId до STATUS_PENDING — PASS, STATUS_CANCELLED (`c0000120`),
1281 мс после отправки CANCEL. Сохранён физический файл `cancel48.bin`
размером 16384 байта: дописано только текущее UART-окно. ECHO после отмены
прошёл. Журнал: `hil\cancel-probe-attach.log`.

Отдельная проверка отмены по AsyncId после штатного 30-секундного
STATUS_PENDING запущена в 00:43:46 (`cancel_async.c`, восемь WRITE по
64 КиБ). В 00:43:56 FILEX-помощник получил `ReadFile error 1167` и
завершился с кодом 1. Нативный клиент через 30562 мс получил один interim,
отправил CANCEL по AsyncId для него и по MessageId для остальных запросов;
за следующие 10016 мс финалы семи незавершённых WRITE не пришли. Итог FAIL
на оборванном UART, не валидный результат отмены при исправном FILEX.
Сохранены `hil\cancel-async-probe.log`, `hil\attach-console.log`,
`hil\attach-exit.log`. Новый тестовый файл `cancel49.bin` не удалялся.

Одно повторное открытие COM4 без сброса ESP в 00:45:11 не удалось:
помощник завершился с кодом 2 (`hil\reattach-console.log`,
`hil\reattach-exit.log`). COM4 и COM5 всё ещё перечисляются Windows,
но действующего FILEX-помощника нет. Для продолжения аппаратных проверок
нужно восстановить перенаправленный UART. Указанный оболочкой код 183
не следует трактовать как надёжную причину CreateFile: прежняя inline-
обёртка вызывает дополнительные функции логирования до чтения LastError.

Успех прямого CANCEL не доказывает, что Explorer послал такой запрос
немедленно при нажатии кнопки. На SMB-проводе этот момент в данном запуске
не записан; точная причина 54 секунд не установлена.
[MS-SMB2 3.3.5.16](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/57bae3d3-5dd7-4a5f-92cb-fc52e2087dad)
различает адресацию отмены по MessageId и AsyncId и требует ускорять её
обработку. Факт надписи «Отмена» в UI сам по себе не доказывает приём CANCEL
сервером.

Версия по указанию пользователя остаётся .91. Апдейтер реального Evo на
192.168.1.113 был проверен только чтением баннера; этот новый образ туда
не отправлялся. Подготовленный `run_evo_update.ps1` НЕ запускался.

## Отдельный опыт Epoch

В `C:\zifi-leaseepoch-20260905-2343` исправлен Epoch в прежнем изолированном
опыте выдачи RWH. MS-SMB2 требует увеличивать Epoch при выдаче новых прав;
клиентская таблица считает переход NONE -> RWH с неизменным Epoch недопустимым:
[сервер](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/fc4f8879-f295-4995-b71e-21f309d8d7c8),
[клиент](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/eaa8f209-3efb-4e12-8e49-ad0d13f7ed41).
Однако видимый Explorer после этой поправки всё равно стоял на 52%.
Копия 7872598 байт завершилась 23:47:37, SHA исходника/backing совпал.
Этот опыт **не исправил индикатор**; выдача RWH из него в прошивку не перенесена.
