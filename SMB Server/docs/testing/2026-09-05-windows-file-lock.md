# Explorer: крупные WRITE не устранили плато; ожидание в RDBSS

Статус: диагностический результат, НЕ исправление SMB-сервера.
Рабочая прошивка `.91`, настоящий ZX-Evo, COM4/COM5 и настройки Defender
не менялись. Все описанные ниже новые копии выполнялись штатным видимым
Windows Shell CopyHere, но сервер был нативной сборкой на ПК, не ESP.
Наблюдения на настоящем ZX-Evo находятся в
[отдельном отчёте](2026-09-05-real091-explorer-fileio.md).

## Проверка гипотезы о дроблении WRITE

Изолированный каталог: `C:\zifi-write512-20260905-0915`. Исходники скопированы
из рабочего дерева `.91`; исходный `smb_server.cpp` сохранён отдельно как
`smb_server.baseline.cpp`. В эксперименте менялись только MaxWriteSize и
credit target. Добавлен запрет компиляции этой версии вне `ZIFI_HOST_BUILD`.
Два варианта бинарников сохранены в `profile8-binaries` и `profile16-binaries`.
Ни один вариант не переносился в рабочую прошивку.

Источник всех копий: JPG, 7 872 598 байт, SHA-256
`8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B`.
Host FILEX моделирует файловые операции на локальном backing-каталоге;
задана скорость 65 536 байт/с. Это НЕ реальные UART, SD или плохой Wi-Fi.
Общее время каждой копии около трёх минут не равно скорости реального ESP.

| Профиль | Виртуальный SMB endpoint | Что Windows реально отправила | Результат UI |
| --- | --- | --- | --- |
| MaxWrite 512 КиБ, 8 credits | `198.18.0.92:445` | 30 WRITE по 256 КиБ + хвост; Charge=4 | Плато осталось |
| MaxWrite 512 КиБ, 16 credits | `198.18.0.93:445` | 15 WRITE по 512 КиБ + хвост; Charge=8 | 52% с 09:40:50 до окончания около 09:42:15 |
| Тот же профиль 16, со стеками Windows | `198.18.0.94:445` | 15 WRITE по 512 КиБ + хвост | Плато после 4 МиБ повторилось |

В этих трёх сетевых захватах все WRITE получили SUCCESS, без WRITE PENDING,
ошибок, FLUSH или CANCEL. Максимум незавершённых сетевых WRITE — два.
Подтверждённые диапазоны покрывают ровно весь файл. После естественного
завершения проверено совпадение SHA-256 исходника и backing.
У профиля 16 на `.93` диапазон 4–4,5 МиБ был отправлен последним.
Следовательно, устранение дробления одного Windows IRP не устраняет
перестановку самих IRP и не является исправлением индикатора.

Отдельно в первом запуске профиля 8 (`198.18.0.91`) второй raw SMB клиент
успешно перечислил пять записей каталога во время копии. Raw CANCEL test44
для 512-КиБ запроса также прошёл на профиле 8: PENDING через 266 мс,
финальный CANCELLED, физически записано только 16 КиБ. Это НЕ проверка кнопки
отмены Explorer и НЕ проверка профиля 16 или памяти ESP. На ПК malloc
не воспроизводит ограничение 2 МиБ PSRAM, поэтому перенос крупных запросов
на ESP без расчёта общей памяти и очередей небезопасен.

Первый PktMon-захват `explorer-smb-full.pcapng` не видел виртуальный endpoint:
он содержит другую, реальную TCP-сессию с `.113`. Для доказательства новых
запусков он НЕ используется. Последующие `wire512.pcap`, `credit16.pcap`,
`stack.pcap` записаны непосредственно в узко ограниченном WinDivert bridge:
запрос до подмены адресов, ответ после обратной подмены, LINKTYPE_RAW,
точное системное время. Эти PCAP не публиковать: внутри данные и SMB-метаданные.

## Что удалось снять в ядре Windows

Последний запуск: START 09:52:42.328, возврат CopyHere 09:56:04.691,
TCP-порт Windows 50623. Время здесь UTC+02:00, Windows build 20348.
Снимались File I/O, CSwitch и стеки; kernel ETL охватывает только
09:52:27.982–09:53:39.990, а не всю копию. Потерянных событий/буферов — 0.
Полные сетевой захват и журнал окна продолжались до завершения.

1. В 09:52:43.7198 MsMpEng PID 5904, TID 5044, начал повторный CREATE
   именно `explorer-stacks512.jpg`. Первая попытка с
   `FILE_OPEN_REQUIRING_OPLOCK` вернула локальный `0xC00000E2`
   (`STATUS_OPLOCK_NOT_GRANTED`). Повтор без этого флага остался в ожидании.
2. В 09:52:44.2196 стек TID 5044:
   `RxCommonCreate -> RxCreateFromNetRoot -> RxFindOrCreateFcb ->
   __RxAcquireFcb -> ExAcquireResourceExclusiveLite -> ExpWaitForResource`.
3. В 09:52:57.9511 Windows поставила WRITE IRP диапазона 4–4,5 МиБ.
   В 09:52:58.4609 у системного рабочего потока TID 3084 записан стек
   `RxFspDispatch -> RxCommonWrite -> RxCommonFileWrite -> __RxAcquireFcb ->
   ExAcquireResourceSharedLite -> ExpWaitForResource`.
4. После успешного WRITE, завершающего первые 4 МиБ, в 09:54:31.9735
   приходит повторный сетевой CREATE, а в 09:54:31.9740 — его SUCCESS.
   Затем Windows отправляет следующие диапазоны не по порядку. Диапазон
   4–4,5 МиБ доходит до SMB только в 09:55:24.5056 и заканчивается
   в 09:55:50.8965, хотя его IRP создан почти тремя минутами ранее.

Таким образом, для CREATE непосредственно измерено ожидание эксклюзивного
FCB-ресурса, для WRITE — ожидание совместного FCB-ресурса. Это согласуется
с правилом Windows: новые запросы совместного доступа ждут при наличии
[ожидающего эксклюзивного запроса](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-exacquireresourcesharedlite).
Но адрес ресурса и связь рабочего TID 3084 с конкретным IRP отдельно не
извлекались. Это сильное указание на механизм, не законченная причинная
проверка и не доказательство, что отключение Defender является решением.
В реальном прогоне `.91` совпадение CREATE/границы 4 МиБ уже измерено,
но его стеки не снимались; не подменять эти два уровня доказательства.

Следующий узкий контроль — тот же файл/сервер/CopyHere, но с временным
исключением только одного тестового UNC-файла из проверки Defender, затем
удаление только добавленного исключения. Это изменение защиты требует
отдельного согласия пользователя; сейчас исключение НЕ добавлялось.
Даже положительный результат такого контроля не заменяет исправление
сервера и проверку обычного Windows-клиента с включённой защитой.

## Воспроизведение и сохранённые данные

- Kernel сбор: `xperf -on PROC_THREAD+LOADER+FILE_IO+FILE_IO_INIT+CSWITCH
  -stackwalk FileCreate+FileWrite+CSwitch`; отдельный Kernel-File сеанс
  `ZifiStackFileIo0954`, keywords `0x3F0`.
- Для расшифровки использованы символы Microsoft. `xperf -a stack` требует
  `-butterfly 1`; результат — HTML даже при расширении `.txt`.
- `kernel-window-cache.csv`: экспорт `xperf -symbols cacheonly ... -a dumper
  -range 15000000 31000000 -stacktimeshifting`; диапазон в микросекундах от начала
  kernel ETL. Значимые строки: 138201–138228 и 2542780–2542795.
- `stack-fileio.csv` — только начальный отрезок копии: 3 завершённых WRITE,
  8 ожидающих WRITE и ожидающий CREATE на момент остановки ETL. Это не обрыв
  копии; её полный успех подтверждён отдельными PCAP и окончательным hash.
- `stack-analysis`, `credit16-analysis`, `wire-analysis-full`: сетевые диапазоны
  и соотношение со шкалой. Для `stack-analysis` полный IRP CSV не передавался;
  нули в IRP-колонках UI CSV не означают отсутствие завершённых IRP.
- `correlate_explorer_fileio.py` дополнен полями CREATE: oplock, access,
  sharing, disposition, options. Повторный разбор реального `.91` сохранил
  результат: 121 WRITE SUCCESS, 16 PENDING, 16 завершённых Windows IRP,
  7 872 598 подтверждённых байт, 0 ошибок WRITE и 0 FLUSH.
