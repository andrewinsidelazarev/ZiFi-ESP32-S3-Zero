# Реальный ZX-Evo: почему стоит индикатор, хотя копирование продолжается

Статус: механизм отставания шкалы локализован по Windows File I/O и SMB.
Исправление прошивки НЕ проверено. Паузы ниже относятся к индикатору Explorer,
а не к прекращению реального копирования.

- Настоящий ZX-Evo `192.168.1.113:445`, Windows `192.168.1.50`, существующее

  SHA-256: `8800C1EABA9A87E73C3C4B3BB6F75D444604CE1E8788FC0FB066AB704028DC5B`.

  перезаписи прежней копии. Видимый Shell CopyHere запущен в обычном окне,

  возврат CopyHere: 08:52:07.695; окно отсутствует с 08:52:08.784.

  наши сеансы записи трасс. Файл назначения оставлен на месте.
- Повторного полного обратного чтения именно этого нового файла не было.

## Что непосредственно измерено

Kernel-File: 16 WRITE IRP — 15 по 524 288 байт и хвост 8 278 байт.
Первые восемь IRP поставлены в очередь Windows за 3 мс в 08:30:25.
Новый IRP добавлялся при завершении предыдущего: начальное окно равно 4 МиБ.
Все 16 завершены успешно, возвращены полные размеры; незавершённых IRP
копируемого файла в конце трассы нет. Корреляция — по Irp и FileObject,
а не только по имени файла или PID. Все WRITE имеют один FileObject.

На проводе: 121 успешный WRITE, сумма и объединение подтверждённых диапазонов
равны 7 872 598 байт, без дыр и перекрытий. Все ответы SUCCESS следуют в порядке
поступления WRITE-запросов: перестановок внутри сервера не обнаружено.
Максимум одновременно незавершённых сетевых WRITE — восемь.

Каждый 512-КиБ IRP соответствует восьми 64-КиБ SMB WRITE. Его завершение в
Windows зарегистрировано через 0,037–0,139 мс после последнего необходимого
SMB SUCCESS. Поэтому в этом прогоне нет потерянного финального ответа,
который оставлял бы уже полностью подтверждённый IRP незавершённым.

FLUSH-запросов к этому файлу — ноль. Промежуточных WRITE PENDING — 16,
все до 08:34:18, то есть задолго до плато после 4 МиБ. Ошибок WRITE — ноль.
Два CANCEL в начале захвата относятся к старым CHANGE_NOTIFY:
ответы CANCELLED имеют команду 15 и AsyncId 32/33, не WRITE.

После первых 4 МиБ Windows послала сначала блоки из диапазона 6–6,5 МиБ.
При его успешном завершении шкала осталась на 52%. Когда завершился диапазон
4–4,5 МиБ, она перешла к 59%. Остальные поздние диапазоны завершались, но UI
оставался на 59% до окончания 4,5–5 МиБ. После этого UI сразу показал 99%.

Вывод из сопоставления: в этой копии шкала ждала завершённого непрерывного
начала последовательности Windows IRP, а не суммы всех завершённых IRP
и тем более не суммы уже подтверждённых 64-КиБ SMB WRITE. Значение внутреннего
callback Copy Engine отдельно не снималось; вывод основан на согласованных
временах UI, начала/конца IRP и сетевых ответов.

Существенная граница: первые байты диапазона 4,5–5 МиБ появились на проводе
только через 17 мин 12 с после постановки соответствующего IRP в Windows.
Сервер не мог приоритизировать ещё не полученные данные. Простое сортирование
очереди WRITE внутри ESP само по себе не устраняет измеренную задержку.

Отдельно зафиксирован запрос метаданных от MsMpEng PID 5904: локальный CREATE
ждал до завершения первых 4 МиБ, а затем быстро обслужился по SMB. Это
совпадение по времени, не доказательство причинности и не основание отключать
Defender. В захвате нет чтений этого файла антивирусом.

## Что из этого не следует

- Не установлено, какое конкретное согласованное свойство SMB или состояние
  клиента вызывает такой выбор следующего IRP. Это ещё требует проверки.
- Нельзя объявлять решением изменение FLUSH, ранний фиктивный SUCCESS,
  перестановку только серверной очереди или очередной произвольный тайм-аут.
- Изолированная последующая проверка MaxWriteSize 512 КиБ и 16 credits
  действительно устранила дробление IRP на проводе, но НЕ плато индикатора.
  Результаты и стеки ожидания RDBSS: [отдельный отчёт](2026-09-05-windows-file-lock.md).
  Этот профиль не переносился на ESP; расчёт PSRAM/очередей не выполнен.
- Этот прогон не является испытанием плохого Wi-Fi или независимым чтением SD.
