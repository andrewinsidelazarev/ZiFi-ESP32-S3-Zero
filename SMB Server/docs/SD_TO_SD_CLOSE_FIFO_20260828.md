# SD→SD: CLOSE после раннего WRITE SUCCESS

## Чистое воспроизведение на ZX Evolution

После установки `s3-native-0.6.78` создание каталога назначения SD→SD стало
успешным, но копирование `\\ZX-Evo\SD\wc` всё ещё завершалось ошибкой. Повторный
захват выполнен без фонового обхода, мониторинга UNC и других параллельных
команд:

- `captures/sd_to_sd_clean_0678_20260828-011317.etl`;
- `captures/sd_to_sd_clean_0678_20260828-011317.pcapng`;
- 10 472 пакета, потерь захвата нет.

Источник содержал 33 файла общим размером 493 625 байт, в назначении осталось
28 файлов и 248 935 байт. Не были сохранены `clock.wmf`, `mounter.wmf`,
`plasmatw.wmf`, `tapm.wmf` и `wplayer.wmf`.

Парсер, разделяющий SMB по TCP-соединениям, обнаружил 23 финальных ответа
`CLOSE` со статусом `STATUS_IO_DEVICE_ERROR` (`0xC0000185`). Перед каждым таким
ответом на проводе не было других незавершённых SMB-запросов. Значит, ошибка не
в лишней сетевой команде и не в сопоставлении одинаковых MessageId разных
соединений.

## Причина

Обычный WRITE получает успешный SMB-ответ после копирования всего payload в
собственный слот PSRAM. Физический `WRITE_AT` через единственный FILEX-мост в
этот момент ещё может выполняться. Поэтому пустой список незавершённых команд
на проводе не означает, что внутренняя VFS-очередь свободна.

Синхронный обработчик `CLOSE` пытался применить отложенный EOF/метаданные и
закрыть FILEX немедленно. Занятый мост возвращал внутренний `bridge-busy`,
который превращался в `STATUS_IO_DEVICE_ERROR`; новый файл помечался сбойным и
удалялся.

## Исправление

В `s3-native-0.6.79` занятый `CLOSE` сохраняет MessageId, номер и поколение
handle, флаги `POSTQUERY_ATTRIB` и общий порядковый номер VFS. Запрос остаётся
во внутренней SMB-очереди и выполняется только после всех более ранних READ,
WRITE, QUERY_DIRECTORY и CREATE. Более поздние физические операции не могут
обогнать его.

После освобождения FILEX прежняя финализация выполняется целиком: дописываются
WRITE этого handle, фиксируется резерв EOF, применяются метаданные, закрывается
физический файл и формируется обычный `CLOSE Response` с исходным MessageId.

## Регрессия и границы проверки

`tools/host_smb/smb_reproduce_test.c`, TEST 33, оставляет первый SMB handle
открытым, запускает ранне-подтверждённый 32-КиБ WRITE второго handle на
искусственно медленном FILEX и сразу закрывает первый. Исправленный сервер
возвращает `CLOSE=0`; свежее открытие читает 32 768 байт, полностью совпадающих
с исходными.

Host TEST 1–31, отдельный медленный PDU-timeout TEST 8, TEST 32 для
CREATE/FINDNEXT и TEST 33 прошли. Сборка прошивки подтверждает только локальную
компилируемость.

## Аппаратный результат 0.6.79 и эталон Samba

Реальный Windows Shell `IFileOperation` на `s3-native-0.6.79` вернул `HRESULT=0`
за 327,8 секунды, но результат оказался неполным. Источник `wc` содержал 33
файла и 489 529 байт, назначение — 31 файл и 392 743 байта. Уцелевшие 31 файла
совпали по SHA-256; отсутствовали `clock.wmf` (75 009 байт) и
`menu\WDC v1.60.$C` (21 777 байт). Чистая трасса без фонового UNC-обхода:

- `captures/sd_to_sd_0679_20260828-131954.pcapng`;
- 10 430 пакетов, потерь захвата нет;
- все 36 WRITE Response успешны;
- 219 CLOSE успешны, 20 CLOSE вернули `STATUS_IO_DEVICE_ERROR`.

Для сравнения тот же Windows Shell скопировал папку между двумя каталогами
одного ресурса Samba 4.24.5 на Fedora. 28 файлов и 17 891 669 байт скопированы
за 12,36 секунды; все относительные пути, размеры и SHA-256 совпали. Трасса
`captures/windows_samba_folder_copy_20260828-140858-v3.pcapng` содержит 2 946
пакетов и 190 из 190 успешных CLOSE.

Команды `QUERY_INFO` присутствуют в обоих потоках и являются штатными
запросами Windows. Основной повторяющийся класс —
`FileNetworkOpenInformation` (`InfoLevel=0x22`): 12 запросов за 12 секунд у
Samba и 563 запроса за 327 секунд у медленного ZiFi. Это периодический контроль
состояния операции, а не посторонний обход каталогов.

Samba поддержала `FSCTL_SRV_REQUEST_RESUME_KEY` и 28 раз успешно выполнила
`FSCTL_SRV_COPYCHUNK`, перенеся на сервере ровно 17 891 669 байт. ZiFi штатно
ответила `STATUS_NOT_SUPPORTED` на 33 запроса ResumeKey, после чего Windows
перешла на обычный READ→WRITE. Отсутствие COPYCHUNK объясняет другой тракт
копирования, но не ошибку CLOSE.

## Оставшаяся причина и исправление 0.6.80

Перед каждым проблемным CLOSE Windows выполняла нормальную цепочку
`SET_EOF → WRITE → SET_BASIC_INFORMATION → CLOSE`. Новый файл оставался открыт
быстрым последовательным FILEX mode=1. `applyPendingMetadata()` считал одного
`ActiveMode::kWrite` достаточным и вызывал `SET_METADATA`, однако
`VfsClient::setMetadata()` разрешает эту команду только в random mode=3. Ошибка
`metadata-not-random` превращалась в `STATUS_IO_DEVICE_ERROR`.

В `s3-native-0.6.80` сервер отдельно запоминает физический режим WRITE. Перед
отложенным `SET_METADATA` последовательный поток коммитится, файл открывается
заново в random mode=3, после чего применяются метаданные и выполняется CLOSE.

TEST 34 повторяет размеры пропавшего `clock.wmf`: SET_EOF 75 009, WRITE 65 536
и 9 473 байта, BASIC_INFO, CLOSE, свежее открытие и полное обратное чтение.
До исправления тест стабильно возвращал `CLOSE=-5`/
`STATUS_IO_DEVICE_ERROR`; после исправления — `CLOSE=0`, 75 009 байт и полное
байтовое совпадение. Полный host-набор TEST 1–34 прошёл.

## Аппаратный результат 0.6.80 и исправление 0.6.81

После OTA `s3-native-0.6.80` тот же Windows Shell скопировал `wc` в
`CODEX_SD_SD_0680_20260828-150623` за 332,11 секунды и вернул `HRESULT=0`,
`aborted=0`. Трасса `captures/sd_to_sd_0680_20260828-150623.pcapng` содержит
10 648 пакетов без потерянных событий. Из 238 CLOSE успешны 237; единственный
`STATUS_IO_DEVICE_ERROR` относится к `plasmatw.wmf`.

Источник содержал 33 файла и 489 529 байт, назначение — 32 файла и 445 497
байт. Все 32 сохранённых файла совпали по SHA-256, включая исправленные
`clock.wmf` и `menu/WDC v1.60.$C`; отсутствовал только `plasmatw.wmf` размером
44 032 байта. Для него успешны `SET_EOF(44032)`, `READ(44032)`,
`WRITE(44032)` и `SET_BASIC_INFORMATION`; финальный CLOSE MessageId 603 вернул
`STATUS_IO_DEVICE_ERROR`. Изолированное копирование того же файла затем прошло
с идентичным SHA-256, поэтому имя и размер не являются причиной.

Остался отдельный риск последовательного mode=1: неполное последнее окно
подтверждается протоколом WRITE_WINDOW до физического APPEND. Редкий отказ
этого APPEND виден только при CLOSE; новый файл к этому моменту уже нельзя
считать полным. В `s3-native-0.6.81` SMB с первого окна использует только FILEX
random mode=3. Каждый WRITE_AT физически подтверждён до SMB WRITE, а
SET_METADATA выполняется без переоткрытия. Mode=1 остаётся только в
`createEmptyFile()` для материализации пустого файла без данных.

TEST 35 моделирует ровно этот отказ для 44 032 байт. На поведении 0.6.80 он
возвращает `CLOSE=-5`/`STATUS_IO_DEVICE_ERROR`; после перехода на random mode=3
возвращает `CLOSE=0`, читает 44 032 байта и подтверждает полное совпадение.

## Аппаратный результат 0.6.81

После OTA `s3-native-0.6.81` Windows Shell тем же `IFileOperation` скопировал
`wc` в `CODEX_SD_SD_0681_20260828-155626` за 326,703 секунды. Клиент вернул
`HRESULT=0`, `aborted=0`. Источник и назначение содержат по 33 файла и 489 529
байт; относительные пути, размеры и SHA-256 всех файлов совпали. Пропущенных,
лишних и повреждённых файлов нет, включая ранее терявшийся `plasmatw.wmf`.

Изолированная трасса
`captures/sd_to_sd_0681_20260828-155626.pcapng` содержит 12 284 пакета; PktMon
сообщил об отсутствии потерянных событий и о 27 отброшенных пакетах. Парсер
восстановил 3 289 SMB-сообщений и 233 пары CLOSE Request/Response. Все 233
ответа CLOSE имеют `STATUS_SUCCESS`; `STATUS_IO_DEVICE_ERROR` отсутствует.
Для `plasmatw.wmf` успешны все шесть CLOSE, в том числе финальный MessageId
602. Таким образом, локальная регрессия TEST 35 подтверждена реальным
копированием SD→SD на ZX Evolution.
