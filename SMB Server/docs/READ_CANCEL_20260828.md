# Отмена копирования SD→PC: трасса и исправление 0.6.82

## Наблюдение на 0.6.81

После нажатия «Отмена» в Проводнике сервер продолжал читать файл с SD. Сразу
после клика были сняты две последовательные пассивные трассы по 45 секунд:

- `captures/cancel_after_click_0681_20260828-202326.pcapng`;
- `captures/cancel_after_click_0681_20260828-202326_cont.pcapng`.

В первой трассе Windows не отправил ни одной команды SMB `CANCEL`, но выдал
новые `READ` по 65 536 байт со смещениями от 2 293 760 до 2 490 368. Во второй
трассе `CANCEL` также отсутствует, а новые `READ` продолжаются со смещений
2 818 048–3 014 656. Это исключает гипотезу о том, что ESP лишь дописывал уже
принятый хвост без новых команд клиента.

Трасса старой прошивки
`captures/zumalvl_upload_0677_explorer_20260827-211226.pcapng` подтверждает, что
обработчик настоящей отмены работал: для READ MessageId 614 сервер сначала
вернул `STATUS_PENDING`, затем Windows отправил точный `CANCEL` по AsyncId,
после чего примерно через 355 мс пришёл финальный `STATUS_CANCELLED` и успешный
`CLOSE`.

## Причина

Сервер выдавал wire-async `STATUS_PENDING` активному READ. По MS-SMB2 кредит
асинхронного запроса возвращается в interim-ответе, а не в финальном. Windows
сразу использовал этот кредит для следующего READ. После каждого финала сервер
продвигал ожидающий запрос, снова выдавал `STATUS_PENDING` и тем самым создавал
самопополняющийся конвейер. Нажатие «Отмена» не доходило до SMB как `CANCEL`, а
копирующий поток продолжал ставить замены.

Нельзя исправлять это нулевым кредитом в `STATUS_PENDING` и возвращать кредит
финалом: для wire-async запроса MS-SMB2 требует выдавать все кредиты в interim-
ответе.

## Исправление 0.6.82

Файловый READ остаётся асинхронным внутри ESP: физические окна FILEX выполняются
вне сетевого callback, ECHO/CANCEL и другие соединения продолжают обслуживаться.
На проводе READ теперь остаётся обычным синхронным запросом:

- `smb2_set_current_request_internal_async()` отключает только внутренний
  120-секундный тайм-аут Request PDU;
- `STATUS_PENDING` и AsyncId для READ не отправляются;
- каждый из четырёх принятых READ удерживает свой SMB-credit до финала;
- уже реализованный `cancelHandler` адресует такой запрос по обычному MessageId.

Без interim-credit Windows не может выдать замену до завершения одного из уже
принятых запросов. После финала копирующий код получает возможность проверить
флаг отмены до постановки следующего READ. Wire-async `STATUS_PENDING` сохранён
для `CHANGE_NOTIFY`, где он нужен протоколу.

## Локальная проверка

- TEST 20: 64 READ по 64 КиБ, у всех `pending=0`, финалы идут строго по порядку,
  данные не повреждены, каждый финал возвращает один credit;
- TEST 24: точный `CANCEL` по MessageId завершает только исходный READ статусом
  `STATUS_CANCELLED`, не расходует MessageId и не ломает последующий ECHO;
- TEST 28: два более старых холодных QUERY_DIRECTORY завершаются до позднего
  READ и без промежуточного READ PENDING;
- полный нативный комплект TEST 1–35 и отдельные timeout/FIFO-регрессии прошли.

Аппаратная проверка Проводником после установки 0.6.82 остаётся отдельным
этапом: локальные тесты не заменяют повторное копирование и нажатие «Отмена» на
реальном ZX Evolution.
