# ZiFi SMB Server для ZX Evolution

Плагин `ZIFISMB.WMF` v0.5.8 и прошивка `s3-native-0.6.82` с выключенным
диагностическим журналом для ESP32-S3 Zero открывают выбранную
SD-карту Wild Commander как сетевой ресурс SMB:

```text
\\ZX-Evo\SD
```

Если имя NetBIOS не находится в конкретной настройке Windows, используйте IP,
который показан в окне плагина:

```text
\\192.168.1.105\SD
```

Параметры готовой сборки:

| Поле | Значение |
| --- | --- |
| TCP-порт | `445` |
| Имя компьютера NetBIOS | `ZX-Evo` |
| Рабочая группа | `WORKGROUP` |
| Общий ресурс | `SD` |
| Пользователь | `zx` |
| Пароль | `zx` |
| Гостевой вход | отключён |
| Подпись SMB | включена |

> [!WARNING]
> Пользователь `zx` получает чтение и запись всего выбранного тома. Сервер
> рассчитан на доверенную домашнюю сеть. Перед первым испытанием сделайте копию
> важных файлов SD-карты.

## Что уже реализовано

- SMB2/SMB3 поверх прямого TCP-порта 445;
- согласование диалектов SMB 2.0.2, 2.1, 3.0 и 3.0.2 библиотекой `libsmb2`;
- вход NTLMSSP по паре `zx` / `zx`, без гостевого доступа;
- подпись пакетов SMB;
- независимые деревья `IPC$` и `SD` внутри одного сеанса Windows/Linux;
- каждый `FileId` принадлежит конкретному `TreeId`; `TREE_DISCONNECT` закрывает
  все дескрипторы дерева до его удаления и не расходует восемь слотов повторными
  подключениями Проводника;
- минимальная служба `srvsvc`: DCE/RPC `BIND` и `NetrShareEnum` позволяют
  перечислить `SD`, когда открыт корень `\\IP-АДРЕС`;
- открытие общего ресурса `SD`, просмотр каталогов и позиционное чтение файлов
  с полным 32-битным смещением;
- ответы на запрошенные Windows контексты `CREATE` `MxAc` и `QFid`;
- асинхронный `CHANGE_NOTIFY`: `STATUS_PENDING`, события создания, записи,
  EOF/атрибутов, удаления и парный rename `OLD_NAME + NEW_NAME`; точный
  `CANCEL` по AsyncId завершает только исходную подписку;
- единый идентификатор объекта в `QUERY_DIRECTORY`, `QFid` и
  `FileInternalInformation`;
- создание файлов, произвольная запись и перезапись существующих диапазонов;
- установка EOF: усечение, обнуление и увеличение файла с нулевым заполнением;
- создание и удаление каталогов;
- удаление, перенос между каталогами, переименование и безопасная замена
  существующего назначения;
- реальные сведения FAT32 о размере/свободном месте, serial и метке тома;
- сохранение поддерживаемых FAT-атрибутов и времён создания/доступа/записи;
- русские имена в UTF-8 с преобразованием в кодировку Wild Commander;
- несколько одновременных SMB-соединений при одном сериализованном физическом
  канале к SD;
- стабильный Samba-совместимый `ServerGuid` из NetBIOS-имени при отдельных
  случайных `SessionId`, чтобы Windows связывал `ZX-Evo` с тем же сервером
  после повторного запуска SMB;
- ответы NBNS по UDP/137 для имён `ZX-Evo<00>` и `ZX-Evo<20>`;
- WS-Discovery по UDP/3702 и метаданные по TCP/5357, чтобы `ZX-Evo`
  появлялся в современном разделе «Сеть» Проводника Windows; WSD Hello
  повторяется каждые 30 секунд для поздно включившихся компьютеров;
- очистка оборванного SMB-сеанса до `accept()` следующего клиента и
  автоперезапуск TCP/445 при нештатном выходе listener;
- состояние клиента, последняя операция и ход текущей передачи в окне,
  сделанном по образцу интерфейса `ZiFi FTP Server`;
- отдельная шкала уровня Wi-Fi в поле `Status`, которая получает RSSI напрямую
  от сетевого ядра и не вызывает `SYS_INFO` или файловые команды;
- остановка сервера клавишей `Esc`.

Фактическая таблица Windows ↔ Samba и сопоставление реализации ZiFi находятся
в [`docs/SMB_PROTOCOL_WINDOWS_VS_SAMBA.md`](docs/SMB_PROTOCOL_WINDOWS_VS_SAMBA.md)
и [`docs/SMB_SERVER_SAMBA_CONFORMANCE.md`](docs/SMB_SERVER_SAMBA_CONFORMANCE.md).

`QUERY_DIRECTORY` обрабатывается по MS-SMB2 3.3.5.18. Поле
`OutputBufferLength` задаёт максимальную, а не обязательную длину ответа.
Готовый PSRAM-снимок сериализуется пакетами до 16 записей; холодный физический
FILEX-путь возвращает одну запись и продолжает тем же курсором в следующем
запросе. Поэтому связанный `CREATE + QUERY_DIRECTORY + QUERY_DIRECTORY`
получает единый compound-ответ после двух `WC_FINDNEXT`, а не ждёт до 32
последовательных операций Z80. Фактическая длина и `NextEntryOffset`
соответствуют сериализованным данным; байты 8-байтного выравнивания обнулены.

Wild Commander предоставляет только один физический курсор каталога, а
Проводник одновременно держит несколько SMB `Open`. Сервер сохраняет
логическую позицию каждого `Open`; при переключении физический курсор
восстанавливается до этой позиции. Холодные `WC_FINDNEXT` выполняются вне
сетевого callback, поэтому медленный каталог не блокирует `ECHO` и соседние
SMB-сеансы. Тот же самый первый физический проход одновременно наполняет
PSRAM-снимок; второго фонового или параллельного обхода каталога нет. Снимок
публикуется только после фактического конца каталога, а первый ответ холодного
каталога никогда не ждёт полного пакетного обхода Z80.

Физические `READ`, `WRITE` и холодные `QUERY_DIRECTORY` входят в одну FIFO-
очередь по порядку прихода SMB-запросов. Уже начатая операция заканчивает свой
запрос целиком, но более позднее чтение файла не может обогнать ожидающий ответ
каталога. Это исключает ситуацию, когда Проводник начинал читать выбранный EXE,
а предыдущий `QUERY_DIRECTORY` того же окна оставался без ответа.

Готовый снимок переживает чтение файлов и метаданных (`STAT`, `QUERY_INFO`),
закрытие дескрипторов и переподключение SMB-клиента. Кэш без таймера живёт до
успешной команды, реально изменившей EVO: создания, записи/изменения
метаданных, удаления или переименования. Такая команда инвалидирует только
затронутый каталог или поддерево; соседние снимки сохраняются. При выходе из
SMB-плагина весь кэш освобождается, потому что SD снова сможет менять другая
программа EVO. Неизвестный `Open` возвращает `STATUS_FILE_CLOSED`, запрос
каталога по обычному файлу — `STATUS_INVALID_PARAMETER`, допустимый, но не
реализованный класс — `STATUS_NOT_SUPPORTED`, неизвестный класс —
`STATUS_INVALID_INFO_CLASS`; запрос свыше 64 КиБ отклоняется как
`STATUS_INVALID_PARAMETER`.

## Сведения о томе

Свободное место — самая дорогая операция VFS: при неизвестном `FSInfo.Free_Count`
она заставляет просканировать активную FAT целиком. Проводник опрашивает его в
течение всего копирования, поэтому учёт ведётся в одном месте — в `VfsClient`,
рядом со знанием о самой FAT. Верхних кэшей-дублёров нет.

- `FatAllocationCache` — единственный владелец числа свободных кластеров.
  Изменение длины файла не выбрасывает карту, а правит счётчик: раньше карта
  сбрасывалась на каждом окне записи и на каждом удалённом файле, поэтому
  следующий же запрос свободного места запускал повторный обход всей таблицы.
- Дельту длины сообщает тот, кто её знает: SMB-сервер уведомляет мост
  операцией `kNoteResize` (прежняя и новая длина). Обратно ничего не читается.
- Операции, объём которых посчитать нельзя — создание каталога, замена при
  переименовании, `OPEN=1` поверх существующего файла — гасят сведения о томе
  целиком через `kInvalidateFsInfo`.
- Запрос свободного места двухфазный. Сначала сервер спрашивает готовый ответ
  (`value=2`): эта фаза не идёт на Z80, поэтому активный файл не закрывается и
  последовательная запись не рвётся. И только при промахе выполняется
  `closeActive` и честное чтение с обходом FAT.

Битовая карта после арифметической правки описывает занятость приблизительно —
номера выделенных Wild Commander кластеров ESP не сообщаются. Точным остаётся
счётчик, а именно его и спрашивает SMB; `allocated()` в прошивке не вызывается.

## Как устроена позиционная передача

SMB-клиент может присылать READ/WRITE порциями до 64 КиБ. Сервер сохраняет
фиксированное окно из четырёх кредитов: это обязательный минимум Windows и его
достаточно для составных запросов метаданных Explorer. Каждый медленный READ
остаётся синхронным на проводе и удерживает credit до финального ответа; внутри
ESP его физические окна обрабатываются неблокирующей очередью. Отсутствие
interim `STATUS_PENDING` не позволяет Проводнику после отмены поддерживать
самопополняющийся конвейер. WRITE сначала целиком копируется в отдельный
PSRAM-слот. Обычный WRITE подтверждается сразу полной длиной и дописывается в
фоне до CLOSE/FLUSH; WRITE_THROUGH подтверждается только после SD. Сервер
подтверждает заранее не более двух ещё не записанных на SD блоков, а следующие
ответы и кредиты удерживает как обратное давление. Поэтому физический хвост
перед `FLUSH`/`CLOSE` не превышает 128 КиБ и не упирается в тайм-аут Windows.

Для SMB используется режим `VFS_OPEN=3` и публичный API 77 `FILEX`:

1. окончательный успешный публичный `FENTRY` сам фиксирует сектор, смещение и
   FAT-запись открытого файла; повторный `TENTRY` не выполняется;
2. ESP передаёт Z80 абсолютное 32-битное смещение командой `VFS_SEEK`;
3. сетевой запрос делится на окна не более 16 352 байт;
4. первые 32 байта страницы занимает блок параметров FILEX, остальные
   `#3FE0` байт — данные;
5. окно проходит по UART кадрами с номером последовательности и CRC-16;
6. Z80 выполняет прямой `READ_AT` либо `WRITE_AT` и подтверждает только
   завершённое окно. Если WC не сохраняет быстрый вызов READ_AT при временной
   подмене страницы `#8000`, чтение автоматически повторяется безопасными
   позиционными блоками по 512 байт через постоянную code-page.

Финальный успешный SMB READ возвращается Windows только после обработки всего
сетевого запроса: Проводник не повторяет непринятый хвост короткого успешного
ответа. WRITE также всегда подтверждает полный запрос; обычный WRITE может
сделать это сразу после независимого сохранения всего payload в PSRAM, а
WRITE_THROUGH ждёт физического завершения. Ни READ, ни WRITE не используют
промежуточный `STATUS_PENDING`; wire-async сохранён для `CHANGE_NOTIFY`.
Зависание до ответа ограничено watchdog раньше обычного PDU timeout.

Поэтому чтение с отметки 700 МБ больше не проходит и не выбрасывает предыдущие
700 МБ: FILEX сразу вычисляет нужный кластер и сектор. Последовательный
16-КиБ тракт `APPEND` сохранён отдельно для FTP и совместимости со старыми
плагинами, но SMB его для файловых смещений не использует.

Два кольца по 64 КиБ переносят данные между сетевым ядром ESP и UART/VFS-ядром.
UART принимается блоками по 256 байт с сохранением хвоста между кадрами, а
payload до 1024 байт отправляется одним вызовом вместо шестнадцати 64-байтных
частей с переключением задачи после каждой.
Каталожный кэш и очередь SMB используют отдельные выделения PSRAM. Для запуска
SMB требуется рабочая PSRAM: сервер заранее резервирует шестнадцать 64-КиБ
рабочих слотов для READ/WRITE. Поскольку физический FILEX-канал один, async
READ-сервис имеет глубину один. Остальные принятые READ представлены маленькими
дескрипторами без PENDING и тем самым удерживают исходные SMB credits. После
финала старейший дескриптор получает рабочий буфер и PENDING; выданный credit
разрешает клиенту прислать одну замену. Поэтому очередь остаётся постоянной и
не зависит от размера файла или числа его 64-КиБ блоков. Выбор физической
операции выполняет общая FIFO для READ/WRITE/QUERY_DIRECTORY, а не порядок
вызовов обслуживающих функций ESP.

Если `FSInfo.Free_Count` неизвестен, FILEX читает именно выбранную
активную FAT. Z80 сворачивает каждые восемь FAT32-записей в байт
карты занятости, а ESP хранит эту точную компактную копию в PSRAM.
Для текущей 32-ГБ карты это 122064 байта вместо примерно 3,9 МБ
сырой FAT. После операции, которая может изменить распределение кластеров,
кэш инвалидируется; следующий запрос Windows строит его заново.

## Быстрый запуск для начинающего

1. Установите совместимый `firmware/firmware.bin` в ESP32-S3 Zero.
2. Скопируйте `WildCommander Improved/exe/WC/FILEX.WMF` в каталог `/WC`
   SD-карты.
3. Скопируйте `SMB Server/build/ZIFISMB.WMF` туда же.
4. В `/WC/wc.ini` поставьте `FILEX.WMF` первой активной строкой секции
   `[PLUGINS]`, а ниже добавьте `ZIFISMB.WMF`:

   ```ini
   [PLUGINS]
   FILEX.WMF
   ZIFISMB.WMF
   ```

5. Убедитесь, что существует `/zifi/zifi.ini` с Wi-Fi-настройками:

   ```ini
   SSID: "Имя сети"
   password: "Пароль Wi-Fi"
   ```

6. Полностью перезапустите Wild Commander: одноразовый провайдер `FILEX.WMF`
   регистрирует API 77 только во время старта.
7. Нажмите `F10` и запустите `ZiFi SMB Server`.
8. Дождитесь шкалы `Wi-Fi [...]`. Запишите показанный IP и состояние NetBIOS.
9. Откройте раздел «Сеть» Проводника и дождитесь компьютера `ZX-Evo`. При
   первом запуске обнаружение может занять несколько секунд.
10. Откройте его или сразу введите в адресной строке `\\ZX-Evo\SD`.
11. Если имя не найдено, введите `\\ПОКАЗАННЫЙ_IP\SD`.
12. В окне входа укажите пользователя `zx` и пароль `zx`. При необходимости
   имя пользователя можно записать как `WORKGROUP\zx`.

Подключение из командной строки Windows:

```bat
net use "\\ZX-Evo\SD" /user:WORKGROUP\zx zx
```

Windows может помнить старые данные входа для того же адреса. Перед повторной
проверкой их можно отключить так:

```bat
net use "\\ZX-Evo\SD" /delete
```

## Проверка целостности файла

Для первой проверки используйте файл больше одного окна, например 40–100 КиБ:

1. вычислите SHA-256 исходного файла командой `Get-FileHash`;
2. скопируйте его на `\\ZX-Evo\SD`;
3. закройте Проводник или дождитесь завершения копирования;
4. скачайте файл обратно в другой локальный каталог;
5. снова выполните `Get-FileHash` и сравните хэши и размеры.

Сообщение Windows об успешном копировании само по себе не доказывает, что SD
прочиталась обратно без искажений. Для аппаратного доказательства нужна именно
новая сессия чтения и побайтовое либо SHA-256-сравнение.

После базовой проверки повторите её с несжимаемым файлом размером 700–800 МБ.
Особенно важен новый сеанс чтения с середины файла: он проверяет, что сервер
передаёт реальное 32-битное смещение в `READ_AT`, а не линейно проходит весь
префикс. Сравните полный размер, SHA-256 исходника и свежесчитанной копии.

## Важные ограничения текущей версии

- Реализован прямой SMB на TCP/445. Старый NetBIOS Session Service на TCP/139
  не реализован.
- Реализован IPv4 WS-Discovery. Автоматическое появление требует, чтобы сеть
  Windows была отмечена как частная, а правила обнаружения сети не блокировали
  UDP/3702 и TCP/5357.
- SMB 3.1.1 временно не объявляется: серверная часть используемой `libsmb2`
  неверно подписывает последний `SESSION_SETUP` этого диалекта. Проверенные
  SMB 2.1, 3.0 и 3.0.2 работают с включённой подписью.
- Реализована только необходимая для Проводника часть `srvsvc` — перечисление
  ресурсов. Административные вызовы Windows/Samba сервер не предоставляет.
- Физический VFS Wild Commander однопоточный: запросы нескольких SMB-соединений
  сериализуются через один канал к SD.
- Физические операции SD остаются однопоточными. Параллельные READ/WRITE
  Windows сначала попадают в независимые 64-КиБ слоты PSRAM, затем
  сериализуются с сохранением их исходных 32-битных смещений.
- Позиционные операции требуют `FILEX.WMF` из Wild Commander Improved.
  Провайдер должен быть первой активной строкой `[PLUGINS]`; без него режим
  `OPEN=3` возвращает `NOT_SUPPORTED`.
- В v0.5.3 исправлен флаг результата `QUERY_CAPS`: ненулевая штатная маска
  возможностей FILEX теперь открывает `OPEN=3`, а не ошибочно отклоняется до
  первого `READ_AT`.
- В v0.5.5 учёт свободного места сведён в один слой (`VfsClient`): карта FAT
  больше не выбрасывается при записи и удалении, а размер растущего файла
  обновляется в снимке каталога точечно. Строка индикации перестала повторять
  одинаковый текст: ход передачи вынесен в отдельное поле `Copying`, которое
  обновляется не чаще четырёх раз в секунду.
- В v0.5.6 асинхронные READ переживают отключение соседнего клиента без сброса
  общей VFS-очереди; `CREATE` сразу материализует новый файл для второго
  CopyFile-handle, а физическая длина синхронизируется между handle. Прошивка
  удерживает не более двух подтверждённых, но ещё не записанных 64-КиБ WRITE,
  поэтому `FLUSH` и `CLOSE` не ждут прежний хвост из девяти блоков.
- В v0.5.7 позиционное чтение вызывает API 77 один раз на всё окно 16 352
  байта. Удалён скрытый fallback по 512 байт, который повторял проверку FILEX-
  контекста и позиционирование 32 раза на окно, то есть 129 раз на один READ
  Windows размером 64 КиБ.
- В прошивке `s3-native-0.6.76` событие `Copying` отправляется после каждого
  завершённого физического окна FILEX. Для размеров от 1 МиБ выводятся две
  цифры после точки, поэтому каждый 16-КиБ шаг виден и на больших файлах.
  Сетевой READ при этом остаётся единым корректным 64-КиБ ответом SMB.
- В прошивке `s3-native-0.6.77` отложенные READ, WRITE и холодные
  QUERY_DIRECTORY помечаются как внутренне-асинхронные до помещения в очередь.
  Поэтому обычный тайм-аут PDU libsmb2 не может удалить исходный MessageId до
  позднего ответа медленного FILEX и оставить Проводник ждать потерянный блок.
- В прошивке `s3-native-0.6.78` новый каталог с `FILE_CREATE` выполняет `STAT` и
  `MKDIR` через общую FIFO физических операций. Параллельный `FINDNEXT` другого
  SMB-сеанса больше не превращает внутренний `bridge-busy` в `IO_TIMEOUT` или
  `ACCESS_DENIED` при копировании каталога SD→SD.
- В прошивке `s3-native-0.6.79` финальный `CLOSE` ставится в ту же FIFO. Ранний
  `WRITE SUCCESS` означает только сохранение payload в PSRAM; закрытие ждёт
  реальной записи FILEX. Аппаратная трасса выявила оставшийся отдельный дефект:
  отложенный BASIC_INFO применялся прямо к последовательному FILEX mode=1 и
  получал внутренний `metadata-not-random`.
- В прошивке `s3-native-0.6.80` сервер различает последовательный и random
  режимы физического WRITE. Перед `SET_METADATA` последовательный поток
  коммитится, файл открывается в random mode=3, после чего метаданные и CLOSE
  завершаются штатно. Host-регрессия повторяет WRITE 65 536 + 9 473 байта из
  аппаратной трассы `clock.wmf` и проверяет 75 009 байт обратным чтением.
- Аппаратная SD→SD проверка `s3-native-0.6.80` сохранила `clock.wmf` и
  `WDC v1.60.$C`, но потеряла один `plasmatw.wmf` размером 44 032 байта. Его
  WRITE и BASIC_INFO были успешны; финальный последовательный APPEND отказал
  на CLOSE. В `s3-native-0.6.81` SMB открывает новый файл для данных сразу в
  FILEX random mode=3. Каждое WRITE_AT-окно физически подтверждается до SMB
  WRITE, поэтому CLOSE больше не публикует отложенный последовательный хвост.
  TEST 35 детерминированно отклоняет такой mode=1: до правки CLOSE возвращает
  `STATUS_IO_DEVICE_ERROR`, после правки сохраняются и читаются все 44 032
  байта.
- Аппаратная SD→SD проверка `s3-native-0.6.81` скопировала все 33 файла и
  489 529 байт каталога `wc` за 326,703 секунды. Пути, размеры и SHA-256
  полностью совпали. В изолированной трассе все 233 ответа CLOSE успешны;
  ранее терявшийся `plasmatw.wmf` присутствует, а его финальный CLOSE
  MessageId 602 вернул `STATUS_SUCCESS`.
- В `s3-native-0.6.82` медленные READ остаются асинхронными только внутри ESP,
  но на проводе не получают interim `STATUS_PENDING`. Каждый из четырёх
  принятых запросов удерживает свой SMB-credit до финального ответа. Поэтому
  нажатие «Отмена» больше не подпитывает копирование новым READ после каждого
  interim-credit; настоящий `CANCEL` адресуется по обычному `MessageId` и
  завершает ровно выбранный запрос `STATUS_CANCELLED`.
- В плагине v0.5.8 поле `Status` после запуска показывает шкалу Wi-Fi и точный
  процент. ESP отправляет её отдельным событием `0x66` раз в две секунды;
  `SYS_INFO`, SMB-команды и FILEX для индикатора не вызываются.
- Не проверено на реальном ZX: предположение, что `GET_FS_INFO` не сбивает
  FILEX-контекст открытого файла и `closeActive` перед ним не нужен. Первая
  фаза запроса и так не идёт на Z80, но при промахе кэша файл по-прежнему
  закрывается — если проверка подтвердит безопасность, закрытие можно снять.
- В v0.5.4 добавлен точный PSRAM-кэш активной FAT для томов, где
  `FSInfo.Free_Count` неизвестен. Фиксированная ёмкость не подставляется.
- Текущий проводной контракт ограничен 32-битным размером и смещением, поэтому
  один файл не может достигать 4 ГиБ. Файлы порядка 700 МБ находятся внутри
  поддерживаемого диапазона.
- Размер, геометрия и свободное место тома берутся из FAT32/FSInfo и
  точной карты активной FAT в PSRAM. Первое сканирование нужно только при
  неизвестном `Free_Count`; повторные запросы используют кэш до его инвалидации.
- FAT хранит только атрибуты read-only/hidden/system/archive и ограниченный
  набор времён. NTFS ACL, alternate data streams и остальные NTFS-метаданные
  не эмулируются.
- Локальная сборка и тесты не являются проверкой на реальном ZX Evolution.

## Сборка и тесты

Для сборки нужен `sjasmplus`. Запустите из этого каталога:

```bat
build.bat
```

Результаты:

```text
build\ZIFISMB.WMF
build\ZIFISMB.lst
build\ZIFISMB.sym
```

Полный локальный прогон:

```bat
test.bat
```

Он собирает WMF, проверяет заголовок, русские комментарии, совпадение кодов
ESP/Z80, legacy-окно `#4000`, позиционное окно FILEX `#3FE0`, команды
`READ_AT`/`WRITE_AT`/`SET_EOF32`/`GET_FS_INFO`/`MOVE_RENAME`/`SET_METADATA`/
`READ_FAT`,
параметры SMB и включённую подпись.

Нативная прошивка собирается из корня проекта:

```bat
build.bat
```

## Где находится код

- `src/smb_server.asm` — запуск, остановка, события и жизненный цикл окна;
- `src/ui.asm` — интерфейс по образцу FTP Server;
- `src/vfs.asm` — legacy-окна 16 КиБ и позиционный шлюз FILEX;
- `src/fs.asm` — пути и преобразование имён;
- `../src/smb_server.cpp` — SMB2/SMB3, NTLMSSP, подпись и NBNS на ESP;
- `../src/ws_discovery.cpp` — обнаружение компьютера Windows и HTTP-метаданные;
- `../src/vfs_bridge.cpp` — межъядерные кольца и синхронизация VFS;
- `../lib/libsmb2` — зафиксированная копия серверной библиотеки;
- `../docs/PROTOCOL.md` — двоичный протокол UART между Z80 и ESP.

Комментарии в исходниках написаны по-русски и объясняют не только действие
инструкций, но и причину ограничений, чтобы проект можно было читать как
практическое пособие.
