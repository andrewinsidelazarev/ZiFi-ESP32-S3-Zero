# Прошивка ESP32-S3-Zero

После запуска `..\build.bat` здесь создаются два разных образа:

- `firmware.factory.bin` — bootloader, таблица разделов и приложение; пишется
  при первой установке по адресу `0x0`;
- `firmware.bin` — только приложение с адресом раздела `0x10000`; не следует
  записывать этот файл по адресу `0x0`.

Образ `s3-native-0.6.87` поддерживает Native `zifi.spg`, NTP, FTP, SMB2/SMB3 и безопасное
обновление по Wi-Fi. В этой версии SMB ограничен проверенным диалектом 3.0.2,
объявляет signing доступным, но не требует его (`SecurityMode=1`; локальная
политика клиента может потребовать подпись), поддерживает формат перечисления каталогов Windows
`FileFullDirectoryInformation`, раздельно учитывает одновременные деревья
`IPC$` и `SD`, перечисляет ресурс `SD` через минимальный `srvsvc`, выдаёт
каталоги потоково по одной записи и публикуется для Проводника через WS-Discovery.
Ответы `CREATE` возвращают запрошенные Windows контексты `MxAc` и `QFid`, а
идентификатор объекта совпадает в `QUERY_DIRECTORY`, `QFid` и
`FileInternalInformation`.
Неподписанный сеанс сохраняет signing key для отдельного контрольного
`FSCTL_VALIDATE_NEGOTIATE_INFO`: подписанный запрос Windows проверяется, а
ответ получает корректную подпись без подписи обычного файлового трафика.
Связанные `CREATE + QUERY_DIRECTORY` возвращаются одной compound-цепочкой.
Холодный `QUERY_DIRECTORY` не строит синхронно полный снимок до EOF, поэтому
первая выдача каталога не удерживает весь compound-ответ на время полного
обхода SD.
512-КиБ WRITE сразу получает interim `STATUS_PENDING`; остальные асинхронные
READ/WRITE получают его, если FILEX не завершён за 30 секунд. Это продлевает
обычный 60-секундный тайм-аут Windows без раннего `SUCCESS`. Перед interim
credit target соединения снижается до одного, поэтому очередь не превращается
в самопополняющийся конвейер; точный `CANCEL` после него приходит по `AsyncId`.
Поле `Copying` обновляется по завершении каждого физического окна FILEX, а не
только целого 64-КиБ SMB-запроса. Для файлов от 1 МиБ счётчик показывает сотые
доли, чтобы каждый 16-КиБ шаг оставался видимым. Скопированный объём равен
сумме уникальных успешно переданных диапазонов одного открытого файла:
внепорядковые WRITE не откатывают шкалу, повторные и перекрывающиеся блоки не
считаются дважды, а `DONE` не зависит от смещения последнего запроса.
Поле `Status` FTP- и SMB-плагинов после запуска показывает 16-сегментную шкалу
Wi-Fi и точный процент. RSSI передаётся отдельным событием `0x66`; `SYS_INFO` и
FILEX для индикатора не вызываются.
Потерянные отдельные пакеты повторяет TCP/lwIP, а Wi-Fi использует
`setAutoReconnect(true)`. Полного продолжения копирования после разрыва TCP нет:
сервер не выдаёт Durable/Persistent Handles, не перепривязывает SMB Session и
FileId к новому сокету и не задаёт отдельные TCP keepalive/`TCP_USER_TIMEOUT`.
Уже принятый WRITE дописывается на SD, но Windows не может возобновить этот же
запрос после переподключения.
Ответ `NetrShareEnum` сохраняет `NULL` во входном необязательном
`ResumeHandle`; Проводник больше не отбрасывает список ресурсов и не повторяет
один и тот же вызов `srvsvc` при открытии `\\ZX-Evo`.
Отложенные READ, WRITE и холодные QUERY_DIRECTORY теперь живут под watchdog
SMB-приложения и не исчезают из `waitqueue` по обычному тайм-ауту libsmb2 до
того, как медленный FILEX успеет вернуть финальный ответ.
Новый каталог с `FILE_CREATE` выполняет проверочный `STAT` и `MKDIR` через ту
же FIFO физических операций. Поэтому копирование SD→SD может дождаться уже
активного `FINDNEXT`, не получая ложный `ACCESS_DENIED` от занятого FILEX-моста.
`CLOSE` файла использует ту же FIFO: ранний успешный ответ на буферизованный
WRITE не позволяет закрытию обогнать ещё выполняющуюся физическую запись.
Все SMB WRITE используют FILEX random mode=3 с первого окна. В отличие от
последовательного mode=1, неполное последнее окно физически записывается до
успешного ответа WRITE и не переносит возможный APPEND-отказ на CLOSE.
`SET_METADATA` выполняется в том же random-контексте. Mode=1 остаётся только
для создания пустого файла, который закрывается до начала SMB WRITE.
Прямой HTTPS проверяет сертификаты по встроенному Mozilla CA-bundle. Стек
сетевой задачи увеличен до 16 КиБ для TLS-рукопожатия, а крупный буфер запроса
вынесен из стека. Поле `NETSTK` в `SYS_INFO` показывает минимальный оставшийся
запас стека после фактически выполненных операций.

В обычном образе диагностический журнал полностью выключен при компиляции.
Отдельный профиль `esp32s3_zero_log` создаёт `s3-native-0.6.87-log`: он хранит
не более 256 записей в кольцевом flash-файле размером 48 КиБ. Скачать этот
журнал после запуска update.sna можно командой
`py -u tools\esp_tool.py --net IP --log zifi.log`. Обычная версия ответит
`ERR log disabled` и не создаёт журнал.

Версия 0.6.7 освобождает оборванный SMB-сеанс до приёма следующего,
автоматически перезапускает TCP/445 после ошибки и повторяет WSD Hello
каждые 30 секунд. Для нового 16-КиБ окна FTP нужен `ZIFIFTP.WMF` v0.13 из
соседнего каталога `..\FTP Server\build`; старый плагин продолжит работать
через совместимый протокол по 512 байт, но без нового ускорения. FTP-порт
появляется только после запуска плагина и успешной команды `FTP_START`; сама
загрузка ESP и подключение Wi-Fi listener не открывают.

## Первая установка через USB-C

1. Извлеките переходник из основной платы. Одновременное питание от USB-C и
   контакта 3,3 В переходником не развязано.
2. Удерживая `BOOT`, подключите USB-C. После появления устройства отпустите
   кнопку.
3. Скачайте официальный `esptool` со
   [страницы релизов Espressif](https://github.com/espressif/esptool/releases).
   Для Windows распакуйте архив `esptool-v4.x.x-windows-amd64.zip` и поместите
   `esptool.exe` рядом с `firmware.factory.bin`.
4. Замените `COM5` в командах ниже фактическим COM-портом модуля и полностью
   сотрите Flash:

```powershell
.\esptool.exe --chip esp32s3 --port COM5 erase_flash
```

5. Запишите полный factory-образ. Параметр `-fm dio` и адрес `0x0` обязательны:

```powershell
.\esptool.exe --chip esp32s3 --port COM5 write_flash -fm dio 0x0 firmware.factory.bin
```

После успешной записи и проверки отключите USB-C и только затем устанавливайте
переходник обратно.

## Проверка прошивки до настройки Wi-Fi

Сразу после первой USB-прошивки работу модуля можно проверить ещё до настройки
точки доступа. Скачайте [`esp_info.sna`](../tools/esp_info.sna), запустите его на
ZX Evolution и дождитесь экрана со строкой `ZiFi/ESP link: READY`.

Программа не читает `zifi.ini` и не подключается к Wi-Fi: она напрямую через
UART ZiFi посылает ESP команды `PING` и `SYS_INFO`. На отдельных строках будут
показаны версия прошивки, свободные RAM и PSRAM, размеры Flash и приложения,
причина последнего reset, распределение задач по ядрам, запас сетевого стека,
буферы VFS и состояние HTTP-прокси. Любая клавиша повторяет проверку.

Такой результат подтверждает, что переходник определяется, ESP запустила
прошивку и двоичный UART-протокол работает. Он не подтверждает подключение к
Wi-Fi или доступ в интернет — их можно настраивать уже после этой проверки.

## Последующие обновления по воздуху

После первой USB-установки один раз запустите совместимую Native-программу,
которая посылает `WIFI_INI` с вашим `zifi.ini` (`zifi.spg` либо
`NTPTIME.WMF`). Прошивка сохранит конфигурацию и дальше сама подключится после
любого reset.

### Для обычного пользователя — без PC

Прошивка `s3-native-0.6.69` добавляет раздельную проверку и автономную установку.
Скачайте с GitHub
[**`ZIFIUPD.WMF`**](https://github.com/andrewinsidelazarev/ZiFi-ESP32-S3-Zero/raw/refs/heads/main/Online%20Update/build/ZIFIUPD.WMF),
скопируйте файл в каталог `/WC` на SD-карте и запустите плагин из меню Wild
Commander. Плагин читает `/zifi/zifi.ini`, а ESP сама по проверяемому HTTPS
получает из GitHub `main`:

1. `firmware/firmware.sha256`;
2. `firmware/firmware.bin`.

Манифест содержит опубликованную версию и SHA-256. До подтверждения плагин
показывает установленную и доступную версии; Flash при этой проверке не
открывается. После Enter ESP повторно читает манифест, требует строку SHA-256
именно для `firmware.bin`, проверяет application-
заголовок ESP32-S3 и полный хэш. Только после совпадения новый неактивный
OTA-слот становится загрузочным, затем ESP отвечает плагину и перезапускается.
Совпадение текущей и опубликованной версии не мешает восстановительно
переустановить тот же образ. `firmware.factory.bin` этот путь не принимает.

Если установленная старая прошивка ещё не поддерживает Online Update, один раз
выполните полную установку `firmware.factory.bin` через USB-C по инструкции
выше. Все последующие обновления выполняются плагином через GitHub без PC,
Python и ручного ввода IP-адреса.
